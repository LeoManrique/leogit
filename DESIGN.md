# leogit — Functional Design

This document covers user-facing **features and flows** — what leogit does, in what order, and how the pieces fit together.

## Product intent

leogit is a desktop Git client for developers who already know git on the command line but want a calm visual surface for the workflows they repeat dozens of times a day: staging, committing, browsing history, switching branches, pushing and pulling. It stays out of the way: every git operation maps to a real `git` invocation against the on-disk repo, so the user can shell out at any moment and the two surfaces stay in sync.

The embedded terminal is part of that contract — it runs in the repo directory and shares the same working tree as the UI.

## Clients

Every flow below is described as the **Tauri client** implements it — the complete, shipping surface on macOS, Windows and Linux. A native **macOS SwiftUI client** is being built alongside it on the same `leogit-core`, and is the lead product going forward; the Tauri app will be re-skinned to match its design once the port is further along.

The native client currently covers the read path, committing, and branch management: choose a folder (a repo root or any subdirectory of one), browse the working-tree changes — one row per file, each showing its whole repo-relative path on a single line and shortening it filename-first when the pane is narrow, the same rule the Tauri list uses — with the selected file's full diff beside them (syntax colour, intra-line change highlights, +/− totals), check the files to include and commit them with a summary + description composer — when exactly one file is checked, the summary placeholder becomes GitHub-Desktop-style "Create/Delete/Update \<file\>" and committing without typing uses it, so the most common commit needs zero typing (no staging area — the checked list *is* the commit, exactly the Tauri semantics; embedded repos ask for confirmation, dirty submodules can't be checked — and the Changes tab carries the working-tree file count in a pill, the Tauri tab bar's badge, so the pending commit's size stays visible from any tab), and browse the commit history at the Tauri client's full depth: the commit list (tag chips, the not-yet-pushed ↑, author · relative time) loads more as it scrolls, and the selected commit shows its whole detail — summary with +/− totals, the full message body in a scrollable block, author with email and absolute date, the complete SHA with a copy button, the files-changed count — over the commit's changed files beside each file's diff at that commit, rendered by the same file list and diff viewer the Changes tab uses. The screen is the Tauri two-column layout as one permanent split: the sidebar (tab bar, the tab's list, and on Changes the commit composer — resizable from its top edge, 180–600 pt, its height remembered across launches) beside the main content (the tab's detail over the terminal dock). The split sits above the tabs, so switching tabs or an empty list swaps only what's inside each column — the divider never jumps, and a clean tree keeps the composer on screen (Commit and Generate disabled) with a faint *No changes* where the list was, exactly like the Tauri sidebar. The composer also **generates the message with AI** (⌘G): a Generate button sends the checked files' combined diff to the local `claude` CLI or a self-hosted Ollama instance — chosen by a provider pop-up beside it, which persists into the same config file the Tauri client reads, so both clients honour one setting — and the result fills summary and description, overwriting whatever was typed, exactly like the Tauri composer; failures show inline in the composer's status strip, and Generate is gated on the provider being able to answer with the same remedy — including the offer to run the fix in the dock below — that the Tauri composer shows. In both clients Commit and Generate lock each other out, so a commit can never land mid-generation and have the late AI result overwrite the freshly cleared composer. Both lists carry the Tauri clients' **row context menus** (flows 3 and 5): right-clicking a changed file offers Discard Changes… — confirmed, and the dialog states which of the two outcomes applies, restored from HEAD or moved to the Trash because the file was never committed — Ignore File / Ignore All \*.ext Files, the two Copy Path items, and Reveal in Finder / Open with Default Program (disabled for a deleted file); right-clicking a commit offers Amend Last Commit…, Undo Last Commit, Check Out Commit… (confirmed, with the detached-HEAD warning), Copy SHA, and Copy Tag. Amend and undo behave exactly as flows 3 and 5 describe, including the composer's amend notice and *Stop Amending*, message-only amends on a clean tree, and undo handing the removed commit's message back to the composer. One deliberate difference: the native lists are single-selection, so there is no "Discard N Selected Changes…". (Both clients identify HEAD by the actual head SHA rather than by the row's position, so the two rewrite actions can never be offered against a commit that merely sits at the top of the loaded page.) A toolbar branch menu — sharing one leading toolbar cluster with the repo switcher, each chip showing icon and name (repo on the switcher, branch on the menu, neither wearing a dropdown chevron — both open on click alike; there is no separate toolbar title or subtitle — the exceptional *detached* and *merging* states ride the branch chip's label) — switches branches (the checkmark marks the current one; picking a remote-only branch creates a local tracking branch), creates a branch off HEAD and lands on it, and force-deletes local branches behind a destructive confirmation. The same menu starts a **merge**: pick a source branch, see how many commits it brings in, and choose Merge or Squash & Merge — a flow the Tauri client has wired but never exposed, so the native client ships it first. Conflicts surface as git's own text plus the conflicted files in the changes list, with a *merging* marker in the subtitle and an Abort Merge action until the merge concludes. The toolbar also **syncs**, through a single adaptive split button at the trailing edge (the where-am-I cluster leads, the action cluster trails) in the GitHub Desktop mold: a strict precedence ladder shows the one action that makes sense right now — *Publish* (no remote), *Publish Branch* (a remote but no upstream, routing the same push through `--set-upstream`), *Pull* when behind (pulling outranks pushing, so a diverged branch always proposes the step that must come first), *Push* when ahead, and *Fetch* once in sync — the button itself stays a stock macOS control, its label weight matched to the leading chips so all three toolbar controls read as one family, and carries no count; the pending counts stand as plain `↑N ↓N` text immediately left of the button (status, not a control — no capsule, no border), spelled out in a tooltip — with Fetch always reachable from the chevron menu and *Force Push (with Lease)* offered there only while the branch has diverged, behind a destructive confirmation. The proposed action is also a menu item — Repository ▸ *Publish* / *Publish Branch* / *Pull* / *Push* / *Fetch* under **⌘P** — which renames itself along with the button, so the shortcut always runs the one thing the toolbar is offering and the menu bar says what that is. There is no separate refresh button: the poll keeps everything current, **⌘R** (View ▸ Refresh) forces the full local reload when wanted, the poll itself surfaces a banner if the repository stays unreadable for several consecutive ticks (and clears it on recovery — both clients do this now), and the branch menu re-reads its list every time it opens — plus whenever HEAD moves — so branches created or deleted in an outside terminal are simply there. Background sync now matches the Tauri client: a 2 s status poll keeps the changes list, history, and ahead/behind counts tracking whatever happens in an outside terminal or editor, auto-fetch runs on the shared `auto_fetch`/`fetch_interval_ms` settings (plus a silent warm-up fetch on repo open, with manual Fetch living on the sync button), re-activating the app resyncs immediately — fetch, silent status refresh, and the open diff re-read, since a file can change on disk without its row changing — and everything pauses while a network operation runs, with a connectivity breaker backing background fetches off when the remote is unreachable. During a transfer a strip under the toolbar shows the aggregate progress bar plus git's own progress line verbatim. One network operation runs at a time, and failures surface as git's text, unedited. When the repo has no remote at all, the sync button reads **Publish** and opens the Publish sheet (name pre-filled from the folder, optional description, private by default) — the same one-shot `gh repo create --source … --remote origin --push` as the Tauri dialog, claiming the same single network-operation slot; on failure the sheet stays open with the fields preserved and gh's error inline, and on success the next refresh moves the button along the ladder to its pull/push/fetch states. A toolbar **repo switcher** (the folder chip) lists every known repository — discovered under the configured scan folders plus recently opened ones from anywhere — each row carrying the working-set indicators: a dirty dot for uncommitted changes, ↓ commits to pull, ↑ commits to push, kept fresh by the same tiered background scheduler as the Tauri picker (recently used repos fetch more often; the open repo's badge rides its own status poll). Filter and click to switch in place — the filter is the same ranked rule the Tauri picker uses (flow 3), with the best match leading so Return opens it — no detour through the welcome screen. Its footer carries **Clone Repository…** and nothing else: in both clients a repo list is exactly what the scan folders cover, so a repository missing from it is a scan-path edit — one that also holds next launch — rather than a one-off open. The list is built as soon as the repository screen appears rather than when the popover first opens, so the first open is already populated; on a cold launch with a deep scan tree, recently used repos appear first and the rest fill in as the folder scan finishes, and the popover says it is still looking rather than claiming there is nothing to find. At launch the native client restores the last opened repo from the state file both clients share, so each resumes where the other left off. An **embedded terminal** docks under the main content — beside the sidebar, never under it — matching the Tauri client's behavior: always-visible header strip, ⌃` (or the header) toggles the 280 pt panel, and the first expand lazily spawns the user's shell — the shared `terminal_shell` setting, resolved to the best shell on the machine — at the repo root, naming what actually launched in the header. SwiftTerm renders it (the native counterpart of xterm.js); minimizing hides the panel but keeps the shell running, + replaces it with a fresh session, ✕ kills it, and switching repos kills the session so shells never leak across repos. The composer can hand it a command — the offer to fix an unready AI provider — which opens the panel, spawns the shell if this is the first expand, and types the command there for you to watch. A shell exiting cleanly collapses the panel; a non-zero exit or a signal death instead keeps the dead terminal on screen with `[Process exited with code N]` in red — VS Code's behavior, in both clients — so a shell that dies instantly (a broken `.zshrc`) no longer flashes its error away. Focus follows the panel: the terminal takes the keyboard whenever it's shown — including the very first expand, so you can type straight away — and hands it back when the panel collapses, so a hidden shell can never swallow keystrokes; typing in it suppresses background auto-fetch just like typing in a text field. **Cloning** is a sheet reachable from the welcome screen and the repo switcher's footer, with the Tauri dialog's two tabs — your GitHub repositories via `gh` (filterable, sortable by recently-modified or name with the toggle shared across clients, `Private` badges, inline error + Retry when `gh` is missing or unauthenticated) and a URL tab taking a full git URL or `owner/name` shorthand — over a shared destination row (pre-filled from the last clone, Browse… opens the native folder picker) with a live *Clones into …* preview; URL clones stream git's real progress bar and raw line, gh clones show an indeterminate one, nothing can dismiss the sheet mid-clone, and a finished clone opens the new repo directly. A native **Settings window** opens with ⌘, (or LeoGit ▸ Settings…), grouped Git / Diff / Repository Discovery / Terminal / AI — only the settings the native client actually consumes: the Diff section carries hide-whitespace, syntax highlighting, and tab size, applied to the open diff the moment they save; theme stays Tauri-side for good (the native app follows the system appearance) and the side-by-side layout until it gets a native design pass. Controls save as you change them (text fields when you leave them) into the same shared config file, and auto-fetch changes re-arm the running loop within one interval — the live re-arm the Tauri client still lacks. There is deliberately no back-to-welcome navigation: repositories are discovered and switched in place, and Welcome only exists until the first repo opens. Flows land one at a time, each verified before the next begins, so treat any flow not named here as not yet ported.

## Top-level flows

### 1. Launch and repo discovery

This flow is the Tauri client's end to end, and it is the one flow the native client does not follow: the `leogit <dir>` hand-off, the second-instance forward, the sole-repo auto-open, the Repo Picker, and the *Create a repository here?* prompt all live only there. The native launch is a single branch of it — restore `last_opened_repo` if the shared state file names one, otherwise show the welcome screen with *Open Repository…* (⌘O) and *Clone Repository…*. Discovery still runs, but it populates the repo switcher rather than deciding what opens.

1. App starts and renders a loading screen while the backend reads `~/.config/leogit/config.toml` (creating defaults on first run) and `~/.config/leogit/repos-state.json`.
2. `gh auth status` is probed in the background; failure is non-fatal. (Its result is currently unread — kept wired for future gh-backed gating; every gh flow's own error text already says what's wrong.)
3. The configured `scan_paths` are expanded (`~` → home) and walked up to `scan_depth` levels (default 3). The first `.git` found in a subtree stops descent.
4. Resolution:
   - If the app was launched from the terminal with `leogit <dir>` (see below), open that repo — even if it lives outside the scan paths — ahead of everything else.
   - If `last_opened_repo` still names a repository, jump straight into the main view — and list it, whether or not this walk found it. Requiring discovery to re-find it dropped a user whose repo lives outside the scan paths back into the picker with the repo they were just in missing from it.
   - If exactly one repo was discovered, open it and persist that as `last_opened_repo`.
   - Otherwise show the **Repo Picker** modal, whose search input uses the same ranked filter as the header switcher (flow 3).
5. Every pre-main phase (loading, picker, error) renders the **same header bar as the main view**, with everything that acts on a repository removed — leaving Settings, Help, and the update chip. Without it those phases were a dead end: discovery finding nothing meant no route to the scan-path setting that would fix it, since the app's only other Settings entry point lives in the main layout, which never mounts without a repo. `Ctrl+,` and `?` work there too.
6. An empty repo list gives three distinguishable answers, in the picker and the main-view switcher alike: *Looking for repositories…* while a walk is running, *No repositories found* with **the folders it searched** listed, or *No matching repositories* when a filter emptied a list that has rows. Searched folders are named expanded — `C:\Users\Leo\Dev`, not `~/Dev` — because that list is there to be checked against what's actually on disk. Both dead ends carry a *Choose folders to search* button, and both lists carry the *Clone Repository…* footer, so "it isn't here" always has somewhere to go.
7. **Discovery re-runs whenever a list is about to be read**: when the switcher opens, and when Settings closes in either phase (by button, Escape, or `Ctrl+,`) — the scan paths are what discovery walks. A repo cloned in an outside terminal, or a folder just added to the scan paths, is therefore simply in the list; the main view used to need a restart for either. Closing Settings deliberately stays on the picker even if exactly one repo now matches, since auto-entering a repo the user never chose is a surprising way for a settings dialog to end.

Defaults fall back to `~/Dev`, `~/dev`, `~/code`, `~/Code`, `~/Projects`, `~/src` when the user has not configured scan paths.

**Paths read the way the OS writes them.** Wherever a repo's location is shown — the switcher's hover tooltip, the picker's empty state, the "Create a repository here?" dialog, error text — it appears as `C:\Users\Leo\Dev\leogit`, not the extended-length `\\?\C:\Users\Leo\Dev\leogit` that Windows' own path resolver hands back. The same path is what a terminal opened on the repo starts in, so its prompt shows a directory rather than a provider-qualified location. A repo row falls back to its folder name when it has no GitHub remote to name it, on every platform. `~` in a scan path means the same folder however the app was started — from a shell, from the Start menu, from Finder — so a configured scan path behaves the same in a development run and an installed one. See [TECHNICAL.md](TECHNICAL.md#path-normalisation).

**Open from the terminal.** The installer adds a `leogit [dir]` shell command (analogous to `code .`): run it with no argument to open the current directory, or with a path to open that repo. Running it inside a subfolder opens the repo that contains it. If LeoGit is already running it focuses the existing window and switches to the repo rather than opening a second one. A bare `leogit`, a path that doesn't exist, or a file just launches/focuses the window. See [TECHNICAL.md](TECHNICAL.md) → *Command-line repo opening* for how the shell function and the single-instance plumbing fit together.

**Not a repository yet.** Pointing `leogit` at a folder that isn't under version control is the common "I just started this project" case, so it offers to fix it instead of doing nothing: a small **Create a repository here?** dialog names the folder, shows its full path, and explains that creating one leaves the files where they are and commits nothing. Confirming runs `git init` (branch `main` unless the user configured `init.defaultBranch`) and opens the new repo immediately — it appears in the repo switcher and becomes `last_opened_repo`, with History showing "No commits yet" until the first commit. Cancelling leaves the app on whatever it resolved to in step 4. The dialog appears in every phase, so it works whether the app was cold-started by the command, was already showing another repo, or is sitting on the picker. Publishing the new repo to GitHub is the existing one-click **Publish repository** flow (flow 7).

### 2. Main view

Two-column layout: a resizable sidebar on the left and a content area on the right, with the embedded terminal docked at the bottom of the content column. The split is permanent — it never disappears for an empty list, and switching tabs swaps only what is inside each column. In the Tauri client all three split widths/heights persist in `localStorage` (`leogit:sidebarWidth`, `leogit:commitHeight`, `leogit:commitFilesWidth`); the native client persists the composer height (`UserDefaults`) and keeps the sidebar and commit-files widths for the session.

**Sidebar** carries a tab bar (`Changes` / `History`) and changes shape per tab:
- *Changes tab:* file list + commit composer. The composer stays visible on a clean tree (the list reads *No changes*, Commit and Generate are disabled) and is resized by dragging its top edge (180–600 px, default 220).
- *History tab:* commit list (virtualized).

**Main content** mirrors the tab:
- *Changes tab:* diff viewer for the active file, which the list keeps filled — the first changed file opens itself on arrival, and again whenever the one that was open leaves the working tree, so the pane is empty only when the tree is ("Working tree is clean"). The remaining state is "No Textual Changes", when a file genuinely has no lines to render — a mode change, a rename, or a whitespace-only edit while whitespace is hidden. (The last of those produces no diff at all; the first two produce a header with no hunks. Both land in the same state, since a blank pane is the same dead end either way.)
- *History tab:* commit detail card + a nested two-pane view (commit files on the left, per-file diff on the right). The commit files pane is independently resizable.

**Header** sits on top of the main content: repo switcher trigger, branch dropdown trigger, ahead/behind indicator, merge state badge, and the action cluster (Pull / Push / Refresh / Settings / Help). The repo switcher opens a popover identical in shape to the branch dropdown — a filter input plus the discovered-repos list (basename + muted path, current repo first and dotted) — and selecting one resets the in-memory repo state, persists `last_opened_repo`, and refreshes status / branches / log / auto-fetch for the new repo without restarting the app. The filter is deliberately loose on a repo's *name* and strict on its *path*: the query's letters need only appear in order in the name (`gpm` finds `git-projects-manager`), while a path has to contain the query outright, and only below the scan folder that found the repo — otherwise the ancestry every repo shares (`/Users/you/Dev/…`) answers almost any short query and the filter matches the whole list. Matches are ranked by how they matched — exact name, prefix, substring, initials, subsequence, then path — and the chosen sort order breaks ties within a rank, so the repo you typed is the one the keyboard cursor starts on. Beside the filter input sits a sort toggle (clock ↔ A→Z, same control as the Clone dialog — orders the list by **when you last opened each repo** or alphabetically, defaulting to recency and persisted across restarts); the open repo always leads, then the most-recently-used, then everything never opened in alphabetical order. Recency of *use*, not of last commit: "where did a commit land most recently" answers a different question — it can easily be someone else's work you just fetched — and answering it cost one `git log` subprocess per repo, fired unbounded in parallel on every open, which reordered the list under the cursor as the timestamps arrived. A footer carries **Clone Repository…** (flow 10), outside the list so it is still there when the list is empty — which is exactly when it is needed. There is deliberately **no "open this one folder" action**: the repo list is what the scan paths cover, so a local repository missing from it means the paths are wrong, and the fix is the setting the empty state already links to — one that also holds next launch, which a one-off open would not. The switcher chip itself is **disabled while a push, pull, or publish is in flight**: there is one global network slot, so switching away would leave the old repo's transfer running with nothing reporting it while the new repo's header read "Pushing…" over a repo that wasn't. Each row carries pull/push badges on its right edge — a `↓ N` (behind) and/or `↑ N` (ahead) reusing the header's Pull/Push arrow glyphs — so you can spot which repos need attention at a glance. Before the arrows, a small **dirty dot** marks a repo with uncommitted changes; it appears exactly when that repo's Changes tab would list at least one file, so the two indicators can never contradict each other. The counts and dot come from the tiered background sync (flow 7), the active repo's own status poll, and a local sweep of the visible rows while the list is open; rows with no remote, no divergence, or not-yet-synced show no badge, and a clean tree shows no dot.

### 3. Staging and committing

- File list shows every change reported by `git status --porcelain=v2 -z`, including untracked files. Each row carries a colored single-letter status marker (see [STYLE.md](STYLE.md), which owns the letters) plus a checkbox. A header row ("3 of 12 files included", with an indeterminate-aware master checkbox) sits above the list and toggles every file's inclusion in one click — it counts what the commit will contain, not what changed, which the list itself already shows; a dirty submodule is in neither figure since it can never be included. An **embedded git repository** (a nested folder with its own `.git`) is shown with a distinct blue ↪ link badge instead of `A`, with a tooltip reading "Nested Git repository — commits as a link, not its files". A **dirty submodule** (a tracked submodule changed inside but whose commit pointer hasn't moved) gets a muted ↪ badge and a **disabled checkbox** — it can't be staged from the parent repo, so it's never auto-selected and never counts toward the commit; the row stays clickable to view its state.
- Selection is opt-out: every detected change starts staged. The set of paths the user explicitly deselected is remembered so that fresh `git status` polls don't re-stage them. When a file disappears from the working tree the deselection forgets it too.
- Clicking a row opens its diff in the right pane and seats the row-anchor at that file. Shift+clicking another row extends a visual multi-row highlight from the anchor through the clicked row (and still activates the clicked row's diff). Pressing **Space** on a focused row toggles that row's checkbox; when the row is part of a multi-row selection, Space bulk-toggles every selected row's inclusion (include all if any are excluded, else exclude all). Shift+clicking a *checkbox* (separate anchor) sets every checkbox in the range to whatever the clicked checkbox is about to become — Finder / Gmail semantics — so the two gestures stay independent.
- **Right-click context menu** (mirrors GitHub Desktop's Changes-tab menu). Right-clicking a row that isn't part of the current multi-selection re-selects just that row first; right-clicking inside a multi-selection acts on the whole set. For a single file the menu offers: **Discard Changes…** (always confirms — see below), **Ignore File (Add to .gitignore)** and, when the file has an extension, **Ignore All .ext Files** (append `*.ext`), **Copy File Path** (absolute) / **Copy Relative File Path**, and **Reveal in Finder** / **Show in Explorer** / **Show in File Manager** + **Open with Default Program** (both disabled for deleted files, and the label tracks the OS). For a multi-selection the menu collapses to a single **Discard N Selected Changes…** since the other actions are inherently per-file. Discard always pops a confirmation dialog, and the dialog says which of the two outcomes applies to *these* files rather than reciting both rules: files that exist in HEAD are reverted to it (`git checkout HEAD --`), while never-committed ones (untracked, staged adds, the new side of a rename) are moved to the **OS Trash** so an accidental discard is recoverable rather than gone. The answer comes from the same decision the discard itself runs on — a row's status letter gets it wrong for a staged re-add, an odd rename, and every file in a repo with no commits yet. Ignoring a file refreshes the status so the newly-ignored entry drops out of the list.
- The diff viewer renders unified diffs with line numbers in both gutters, optional syntax highlighting, and an optional side-by-side layout. The `tab_size` and `hide_whitespace` settings are honored live (changing `hide_whitespace` re-fetches the current file's diff). Long lines always wrap to the pane — the GitHub Desktop model. Binary files (where git can't produce a line-by-line diff) keep their file-header but the body is replaced with a "This binary file has changed." stand-in. A **dirty submodule** likewise replaces the diff with a **"Submodule changes"** message explaining its modified content must be committed inside the submodule before it can be part of this repository — instead of the opaque `Subproject commit …-dirty` line git would otherwise show.
- A selected file with **nothing to show** gets a pane that says which nothing it is: the file matches its committed state, the change is entirely whitespace and the setting is hiding it, or the file changed without changing any lines (a mode change, a rename). One caption covering all three told the user a file was unchanged when a setting was simply hiding the change.
- A **very large diff** — over 4 MB, or with a single line over 5 000 characters — is withheld rather than rendered, with its measurements and a *Show diff anyway* button. Both clients do this. It withholds, never refuses: the escape applies to that one request, so moving to another file gets the guard back. The long-line case matters on its own — a minified bundle or a lock file is slow to render at a total size the size bar waves through.
- Syntax highlighting runs entirely in Rust (syntect + two-face extended SyntaxSet). The backend returns token-class indices, the frontend layers them as `.syn-*` CSS classes, and each `.syn-*` class reads its colour from `--syn-*` CSS variables defined on `[data-theme]`. Toggling light/dark is therefore a pure CSS swap — no re-fetch, no re-tokenize, no WebView grammar cache.
- When a hunk has the same number of consecutive delete and add lines, the backend pairs them up and annotates each line with the character range that actually changed (longest-common-prefix / common-suffix). The viewer overlays a brighter backplate on just that range on top of the syntax-coloured tokens, so `Relay` → `Metrics` inside an otherwise identical line gets called out without losing the syntax colour. Lines longer than 1024 characters skip both the annotation and the syntax tokenisation to avoid noisy diffs and runaway parser time.
- Switching files keeps the previous diff on screen until the new fetch resolves — the common case, fast enough that the swap looks instantaneous. Past 150 ms the pane says so by dimming what is on screen and laying a spinner over it; it never blanks. What is showing is still the truth about the file the user was reading, and unmounting it threw away the rendered rows, their colouring and the scroll position on every slow load, including the ones that came back identical. Stale in-flight fetches are dropped if the user has already moved on. Both clients, and the same treatment for commit-detail file switches.
- A diff that fails to read says so **inline, where the diff would have been**, with the stale one cleared — never behind a dialog describing one file while another is rendered. Nothing else is blocked: the rest of the repository is on screen and correct, and clicking the row again re-reads. Both clients.
- A submodule that changed inside without its recorded commit moving is answered before any read: git would only report an opaque `Subproject commit …-dirty` line, so the pane explains that the changes must be committed inside the submodule first. Both clients — and neither spends a subprocess finding out.
- The diff viewer mounts every row: it is deliberately **not** virtualized, because wrapped lines have variable heights and the fixed-height offset math windowing depends on cannot survive that. Wrapping is the property worth keeping, so the trade goes that way. The diff body scrolls vertically only — line content is `pre-wrap` with `overflow-wrap: anywhere`, so even an unbroken run (a long URL, a minified blob) folds into the pane instead of pushing a horizontal scrollbar. Side-by-side columns wrap the same way and grow vertically rather than clipping, so the two sides stay row-aligned.
- Commit composer at the bottom of the sidebar has a single-line **Summary** input with a 72-character soft counter (turns yellow past the limit) and a multi-line **Description** textarea.
- **Commit** runs `git reset -- .` first to clear the index (the pathspec form works even on a fresh repo whose HEAD is unborn, where `git reset HEAD` would fail — so the very first commit in a brand-new repo goes through), then re-stages only the user's selected paths (removals go through `update-index --force-remove`; additions/modifications go through `git add`, which also correctly stages an embedded repo as a gitlink), then pipes the formatted message to `git commit -F -`. The message is built via the backend's `format_commit_message` so co-author trailers stay consistent.
- **Committing an embedded repository** pops a confirmation first ("Commit nested repository as a link?"). It explains that the folder commits as a **link** to its current commit — the folder's files won't be copied into the outer repo, and anyone cloning won't get them unless it's set up as a submodule. Confirming stages the gitlink and commits; cancelling leaves everything untouched. This fires every time (embedded repos are rare and stop appearing once committed), so there's nothing to remember or un-remember.
- **Amend last commit** is reachable by right-clicking the topmost commit in History → "Amend last commit…". The composer enters amend mode: summary and description are pre-filled from the commit (Co-Authored-By trailers are extracted and re-applied via `format_commit_message`), a notice band reads "Your changes will modify your most recent commit. [Stop amending]", the primary button label swaps to "Amend commit", and the must-select-files gate is relaxed (message-only amends are allowed). On commit, the backend runs `git commit -F - --amend`. After amending a commit that was already pushed, the header naturally surfaces `↑ 1 ↓ 1` and the user can complete the workflow via the Force push (with lease) item in the push button dropdown.

### 4. AI commit message generation

- The composer has a provider dropdown (Claude / Ollama) and a **Generate** button. The dropdown reads from and writes back to the persisted `ai_provider` config — the same source of truth as the Settings overlay — so the choice survives restarts and the two stay in sync. Switching provider never needs a Settings trip: each provider keeps its own model, so Generate always runs against something that provider actually has.
- Generate sends the unified diff of the currently selected files only (untracked files are diffed via `--no-index`). The diff goes to the chosen provider with a strict JSON prompt.
- **Claude**: shells out to the `claude` CLI (`--print --output-format json --model <model>`). Model defaults to `sonnet`. Diff size is capped at 20 MB.
- **Ollama**: posts to `http://localhost:11434/api/generate` (or `ollama_server_url`). Model defaults to `tavernari/git-commit-message:latest`. Diff size is capped at 50 MB.
- The JSON response is parsed flexibly (accepts `title`/`summary`/`subject`/`message` and `description`/`body`/`details`). If parsing fails, the first line becomes the title and the rest becomes the description.
- Both providers run with a 120-second timeout. Whatever went wrong appears in **one strip** below the description: the failure of the last attempt, and under it the standing reason an action is unavailable. Two lines at opposite ends of the box, saying the same thing in different words, is what that replaced.
- **Generate is disabled when the chosen provider can't answer** — which is not the same as not being installed. A Claude CLI that is present but signed out passes every "is it there" check and fails every request, so the app asks both questions: `claude --version` and `claude auth status` for Claude, a request to its own configured address for Ollama. It says which one failed in the strip ("Claude is installed but not signed in.") rather than leaving it to a hover. The answer stays on screen while it is being re-checked, so nothing blinks in and out as you come back to the window.
- **When there's a command that would fix it, the app offers to run it in its own terminal** — `Run claude auth login`, spelled out, because it is about to type into your shell. The terminal panel opens, the real CLI runs there, your browser handles the sign-in, and you answer the CLI's own prompt. The app deliberately does not drive that flow itself: it would mean rebuilding a terminal next to the one already in the window, and asking for an auth code in app chrome is a habit worth not teaching. Ollama gets the same treatment only when its address is on this machine — pointed at a server, the fix is on that server.
- **A session that expires while you work is caught by the request, not the check.** Signing out removes the credentials, so the check sees it; an expired session leaves them in place, so the check still reports you signed in and only a real Generate finds out. A failed Generate is therefore read the same way, and what it produces **takes the place of** the raw failure rather than sitting under it — one sentence you can act on beats two saying the same thing. The CLI's own words stay a hover away.
- **Nothing stays disabled after you've fixed it.** Every remedy takes you out of the app — a browser for the sign-in, a terminal for the rest — so coming back re-asks. While the check is still out, or if it returns something the app can't read, Generate stays enabled: a request that reports its own failure beats a button refused on a guess.
- Both clients do all of this, in the same words.

### 5. History browsing

- Commit list is virtualized (50 px rows) and pages 50 commits at a time, prefetching when the user is within 200 px of the bottom. The list is **append-only and rooted at HEAD**: `commits[0]` is always the repository's HEAD, paging only adds older rows to the end, and nothing is ever dropped from the front — so the rows on screen keep their positions and there is no scroll to compensate. Both clients run this model; only the page size differs (50 here, 100 natively), which is a scroll-feel choice. When HEAD moves — a commit, a checkout, an undo — the log is re-read from the top rather than patched, as deep as the user has paged and no deeper than 500 commits, dropping the oldest rows; they re-grow by scrolling. The list then goes to row 0, where the commit that just happened is.
- Arrow keys move through the commit list, Home/End jump to its ends, and the rows scroll into view as the selection moves — the same keyboard the changed-file list has. Right-clicking a row selects it first, so the menu and the detail pane always describe the same commit.
- The newest commit is selected on arrival, and the selection re-seats whenever a re-read drops the commit that was selected — which is what amending or undoing does to it. Both clients follow those two conditions and no others, so a rewritten-away commit's detail can never stay on screen.
- Each row is two lines. First line: the commit summary plus right-aligned indicators — a tag pill (e.g. `v0.1.0`, with a `+N` pill when a commit has multiple tags) and the "not yet pushed" arrow (any local commit not yet on the remote — which includes every commit on a branch that hasn't been published, where the base it branched from stays unmarked, exactly like GitHub Desktop). Second line: the author name · a humanized relative date (`just now` / `Nm ago` / `Nh ago` / `Nd ago` / locale date past a week) that self-refreshes every 10 s (gated on visibility — skipped when the History pane is hidden or the window is backgrounded) so an open History tab never goes stale. The SHA is not shown in the list (it's a row away from useful and the detail card carries it); the right-click menu's "Copy SHA" covers the copy case.
- A freshly initialized repo with no commits yet shows a centered "No commits yet" empty state instead of a blank pane (gated on the log having finished its first load, so a repo that *does* have commits never flashes the message while the initial `get_log` is in flight). The detail pane beside it says the same thing rather than inviting the user to select a commit from a list that has none — the two states are told apart, in both clients.
- Selecting a commit loads its detail card (full message exactly as git reports it, trailers included; author with email; the absolute date; the SHA with copy-to-clipboard) and its file list. The first file's diff opens automatically. Re-selecting the commit already open does nothing: a commit's identity is its SHA, so there is nothing a second read could return.
- Per-file commit diffs use `git log -1 -p --first-parent` to produce a proper unified diff (not file contents).
- Right-clicking a commit opens a context menu: "Amend last commit…" and "Undo last commit" — both rewrite `HEAD`, so both are offered only on `HEAD` itself, with Undo further gated on the commit being unpushed — **"Checkout commit…"** (offered on any commit that isn't `HEAD`, since checking out `HEAD` is a no-op), then "Copy SHA" (full hash) and "Copy Tag" (enabled only when the commit is tagged; space-joins multiple tags). An ellipsis means the item asks something before it acts, so it tracks what each one does: amend hands the message to the composer, checkout confirms, and undo — which runs immediately, losing nothing the composer and the working tree don't now hold — carries none. The same menu primitive will host future actions (Reset / Revert / Cherry-pick / Create branch from).
- **Checkout commit** mirrors GitHub Desktop: it first pops a confirmation dialog explaining that checking out a commit creates a *detached HEAD* (you'll no longer be on a branch), then runs `git checkout <sha>`. Once detached, the branch chip shows `On <short-sha>` with a commit icon, a `DETACHED HEAD` marker sits where the sync state usually reads, and Push/Pull are suppressed (there's no branch to push). The user returns to normal by picking a branch from the branch menu — nothing about their branches changed. A checkout that would clobber uncommitted edits is refused by git and surfaced as an error rather than losing work.

### 6. Branches

- The header branch button opens the **Branch Dropdown** overlay: local branches first, then remote branches, sorted by most recent committer date.
- Switching to a **local** branch is a `git checkout <name> --`. Picking a **remote** branch (e.g. `origin/feature`) checks out a local tracking branch instead of landing in detached HEAD: the local name drops the remote prefix (`origin/feature` → `feature`, `origin/team/x` → `team/x`) and is created with `git checkout -b <local> --track <remote>`; if that local branch already exists it's simply switched to. Status and branch list refresh automatically.
- **Create branch**: inline input in the dropdown; new branch is created from the current HEAD and immediately switched to.
- **Delete branch**: row-level X icon on local branches (only non-current). Confirmation step before `git branch -D`.
- Other supported commands with no UI here: rename, delete remote branch, merge, squash merge, merge abort. The merge overlay exists and is mounted, but nothing opens it — the native branch menu is where that flow is reachable today. Merge *state* is not in this list: `MERGE_HEAD` drives the header's `MERGING` chip (flow 7).

### 7. Remote synchronization

- **Header buttons**: Pull (`git pull --ff --progress --recurse-submodules`) and Push (`git push --progress`, auto-adds `--set-upstream` when no upstream is configured). Each shows a small numeric badge with the behind/ahead count (`Pull (2)`, `Push (3)`). **Pull only renders once the current branch has an upstream** — before that there's nothing to pull from, so only the publish affordance shows (matching GitHub Desktop).
- **Live transfer progress** (mirrors GitHub Desktop): while a push or pull runs, the button's label flips to `Pushing…`/`Pulling…` with a spinner, a subtle full-height fill wipes across the button tracking the aggregate transfer percentage, and git's own progress line — phase, object counts, throughput, e.g. `Writing objects:  53% (531/11939), 19.06 MiB | 1.38 MiB/s` — appears verbatim in the header's status area beside the branch chip. Push and Pull are mutually exclusive while one runs (the other button disables), and the rest of the app stays fully interactive: browsing diffs, history, and even committing keep working mid-transfer.
- The Push button is a split button: the main face triggers a plain push; a chevron on the right opens a small dropdown. The dropdown lists "Push" plus a "Force push (with lease)…" item that appears **only when the branch has actually diverged** (commits on both sides — `hasUpstream && ahead > 0 && behind > 0`); an ahead-only branch fast-forwards, so offering force push there would be noise. Force push opens a confirmation dialog explaining that `--force-with-lease` will overwrite the remote branch but will refuse the push if someone else has pushed since the last fetch. leogit never uses bare `--force`.
- **Publish branch**: when the repo *has* a remote but the current branch has no upstream yet (`hasRemote && !hasUpstream`), the split button shows a **"Publish branch"** face (upload icon) instead of "Push", and the dropdown collapses to a single "Publish branch" item — mirroring GitHub Desktop. Clicking it runs the same push as normal but with `--set-upstream`, so the branch is created on the remote and starts tracking in one action; the next status refresh sees the upstream and the button becomes a plain Push. The ahead badge is suppressed in this state so the publish affordance reads as the single thing to do — not because the counts are unknown: when a matching `refs/remotes/<remote>/<branch>` exists, core computes ahead/behind against it even with no configured upstream (deliberately without claiming `has_upstream`, which is what still routes the first push through `--set-upstream`).
- **Publish to GitHub**: when the repo has no configured remote (`status.has_remote === false`), there's nowhere to push, so the split button reverts to a "Publish" face (cloud-up icon) and the dropdown shows a single "Publish to GitHub…" item. Both open the Publish dialog ([PublishRepository.svelte](apps/tauri-app/src/lib/components/PublishRepository.svelte)) — GitHub.com only (no Enterprise tab), with Name (pre-filled from the repo folder), Description, and a "Keep this code private" checkbox (private by default). Confirming runs `gh repo create <name> --source <repo> --remote origin --push` so it creates the repo under the user's `gh` account, wires up `origin`, and pushes the current branch in one shot. On success the next status refresh flips `has_remote` true and the button returns to normal Push.
- **Auto-fetch**: when `auto_fetch` is true, a background timer runs `git fetch --prune --recurse-submodules=on-demand` against the first remote every `fetch_interval_ms` (default 30 s). Fetches are skipped while the user is typing in an input or while the window is hidden.
- **Status polling**: every 2 s the frontend re-runs `get_status` silently and polls `git rev-parse HEAD`. If the SHA changed (commit/checkout/external `git` action) the commit log refreshes automatically. When the app regains focus or visibility it runs the same status/HEAD resync immediately, **fetches the active repo's remote** (so a moved upstream surfaces on the Pull button right away — previously it only refreshed on the 30 s timer), and re-fetches the diff of the file open in the changes pane, since it may have been edited on disk while the app was in the background.
- **Freshness while unfocused (native macOS decision)**: the open repo never goes stale just because the window isn't frontmost — or isn't even visible. Losing focus slows the status poll (2 s → 10 s); hiding or minimizing the window slows it further (30 s) and stretches auto-fetch to 3× its configured interval, so bringing the window back reveals a screen that is already current instead of one that visibly catches up on arrival. Only the *other* repos' badge machinery pauses while the app is inactive, and the on-focus resync catches it up. (The Tauri client still pauses everything while hidden — the two bullets above describe it; the divergence is recorded in FRONTEND.md §8.)
- **Tiered background sync** ([repoSyncScheduler.ts](apps/tauri-app/src/lib/services/repoSyncScheduler.ts)): so the repo picker can show each repo's pull/push state without opening it, a scheduler fetches the *other* recent repos on a cadence that decays with recency. Tiers are sliced from a most-recently-opened list (`recent_repos`, persisted), with the active repo excluded (it already has the 30 s auto-fetch + 2 s poll): the next 4 ("top 5") every 2 min and on refocus (throttled to once / 30 s), the next 5 ("top 10") every 5 min, the next 10 ("top 20") every 10 min, and the long tail when you switch to it — or, without any network cost, whenever the repo list is open (a local sweep keeps every visible row's badges and dirty dot current, even offline). Each repo is refreshed via `repo_sync_status` (a lighter `git fetch` + ahead/behind that skips the working-tree scan); within a tier the repos are walked sequentially to keep concurrent `git fetch` processes low. Switching to any repo fetches it immediately and promotes it to the front of the list.
- Ahead/behind counts and merge state come from the porcelain v2 branch headers; the header shows `↑ N ↓ N`, and a `MERGING` chip when `MERGE_HEAD` exists.
- **Offline / flaky behaviour**: the app stays smooth when there's no connection — no spinners that never end, no frozen window, and deliberately **no scary banners**. Every remote command is time-boxed and runs off the UI thread, so a Pull/Push you click while offline fails quickly with an inline error instead of hanging, and the rest of the app stays interactive. Background work (auto-fetch, the tiered picker sync, the on-refocus refresh) quietly stops firing while the machine is offline or the link is flaky — badges simply hold their last-known counts rather than churning — and resumes on its own the moment connectivity returns (or the next time a manual action succeeds), refreshing immediately so nothing looks stale for long. See TECHNICAL.md → *Network resilience* for the mechanics (per-call timeouts + a connectivity circuit breaker).

### 8. Embedded terminal

- Docked at the bottom of the main content area — under the diff, never under the sidebar. Expanded, the whole dock is 280 px tall in the Tauri client, header strip included; the native dock puts the 280 pt on the emulator alone, under its own 28 pt accessory bar.
- Toggle with **⌃`** or the header chevron. (The Tauri handler accepts either modifier — it is cross-platform; the native client takes Ctrl only, since macOS owns ⌘` for cycling an app's windows.) A separate `+` button replaces the shell with a fresh session; the X button kills the current PTY.
- Whenever the section is shown — first open, a new session, or re-expanding from minimized — the terminal grabs keyboard focus so you can type immediately without clicking into it.
- Spawns a shell with the repo path as cwd — in the OS's ordinary path form, so the prompt reads `PS C:\Users\Leo\Dev\leogit>` rather than a `Microsoft.PowerShell.Core\FileSystem::` fallback, and `$PWD` is something scripts can work with. The shell is the user's choice (Settings → Terminal), defaulting to the best one found on the machine: on Windows **Git Bash** → PowerShell 7 → Windows PowerShell → Command Prompt; on Unix `$SHELL`. Only shells that actually exist are offered, and a preference whose shell was uninstalled silently falls back rather than failing to open.
- The shell that actually launched is named in the panel header, so what you get is never a guess.
- The child inherits the real Windows `PATH` (the system+user registry merge, same as any other app gets) rather than whatever environment happened to launch LeoGit — which is what previously made most commands fail when the app was started from Git Bash.
- xterm.js handles rendering; FitAddon syncs cols/rows to the backend on resize (debounced, so dragging the panel doesn't corrupt the prompt). Output is streamed back via per-pid Tauri events (`terminal-output-<pid>`); `terminal-closed-<pid>` fires when the shell exits, carrying the reaped child's exit code and fatal signal. A clean exit collapses the panel; anything else keeps the dead terminal on screen with `[Process exited with code N]` in red (VS Code's behavior) — the panel's ✕ still closes it. One gap remains at the very start of a session: the two per-pid listeners are registered two async IPC round trips *after* `start_terminal` returns, and an event emitted with nothing listening is dropped, so a shell that dies inside that window can lose both its error output and its exit notice. Non-ASCII output — box drawing, accents, emoji — survives intact regardless of where it lands in the byte stream.
- Switching repos kills the active terminal session so we never leak shells from a prior repo.

### 9. Settings

A modal overlay grouped into Appearance / Diff / Terminal / Git / AI / Repository discovery. Saving sends a **patch** of just the fields this form owns, so a setting the other client changed while the overlay was open survives instead of being reverted — and the corrected config comes straight back into the form, because the backend clamps every numeric field to its range and treats an emptied text field as "no value" rather than as the empty string. A typed-past-the-limit or emptied field therefore can't reach the shared file, where it would land in the *other* client's rendering or fail with a parser error the user has no way to read; the fields' own minimums and maximums come from the same declaration that enforces them. Every save re-reads the file into the client's config store, so theme changes apply immediately and diff settings (`hide_whitespace`, `syntax_highlighting`, `side_by_side_diff`, `tab_size`) re-render the active diff. The file is **also re-read whenever the window becomes active again**, because the native client writes to the same file: a save made there used to never reach a running Tauri window at all, leaving theme, diff settings and provider at their launch values for as long as the app stayed open. `fetch_interval_ms` and `auto_fetch` are the exception: the fetch timer is armed when a repository opens and is not re-armed by a save, so a changed interval takes effect on the next repo switch or launch.

The AI section shows **one provider's settings at a time** — Claude's model and timeout, or Ollama's model, server URL and timeout. Each provider remembers its own model: one shared field meant a model chosen for Claude was handed to Ollama, which has never heard of it, and Generate failed with nothing on screen explaining why. The timeout is now read, too — it used to persist a value nothing consumed, which is worse than not offering the control.

### 10. Cloning a repository

- **Clone Repository…** in the footer of *both* repo lists — the startup picker and the main-view switcher — opens the **Clone dialog**, a modal with two tabs. It is reachable from the picker because the user with no repository to open is the one most likely to want to clone one; when it lived only inside the main-view switcher, that user was the only one who couldn't reach it.
  - **GitHub** — runs `gh repo list` (your non-archived repositories, forks included, 200 max) into a filterable list sortable by **Recently modified** (default, on `pushedAt`, ties broken by name) or **Name** (the toggle is persisted across restarts); each row shows `owner/name`, a `Private` badge, and the repo's description as its tooltip. The list is fetched once and kept for the app run — `gh repo list` takes seconds, and paying that on every open made the dialog feel broken — with a **Refresh** button beside the filter for a repo created since launch. The filter stays live while a fetch runs. Cloning a selection uses `gh repo clone` so it inherits the user's `gh` auth (private repos need no prompt). If `gh` is missing or unauthenticated the list shows the error inline with a Retry. Empty results distinguish *you have no repositories* from *none match your filter*.
  - **URL** — a free-form field accepting a full git URL or `owner/name` shorthand (expanded to `https://github.com/owner/name`); cloned via plain `git clone` with `GIT_TERMINAL_PROMPT=0` so an unauthenticated clone fails fast instead of hanging on a prompt.
- A **Local path** field is the parent folder the repo lands in, with a **Browse** button that opens the native folder picker (Tauri dialog plugin). It defaults to `last_clone_dir` (the folder used last time), falling back to the first `scan_path`, then `~/Dev`. A live preview shows the final `parent/repo` path; the backend expands a leading `~`.
- **Return clones**, from anywhere in the dialog, whenever the Clone button is enabled. In the GitHub list, Return on a row the cursor hasn't picked yet selects it first, so cloning from the keyboard is arrow-arrow-Return-Return: the second press acts on a destination path the first press made visible.
- Reopening the dialog keeps the **tab** and clears the **inputs**. The tab is a preference ("I clone by URL"); the URL, filter and selection are one clone's worth of intent, and carrying those over meant reopening on a stale selection with Clone already lit.
- While a clone runs, a thin progress bar plus git's raw progress line (`Receiving objects: 42% (…), 12.4 MiB | 3.1 MiB/s`) appear above the dialog's footer — both tabs, since `gh repo clone` forwards `--progress` to `git clone`. Everything that chooses *what* to clone is frozen and dimmed for the duration: there is no cancel, so an editable dialog could only lie about where the bytes were going. The progress strip itself stays bright.
- On success leogit remembers the parent folder (`last_clone_dir`), adds the cloned path to the in-memory repo list, and opens it immediately — no restart or re-scan needed (the repo need not even live under a configured scan path).

### 11. Update available

leogit checks GitHub Releases once per launch (silently — a failed check never surfaces). The chip only appears once the new release actually carries a build **for your platform**: releases are uploaded one platform at a time, so for a while a release exists that you can't yet install — offering it would just dead-end you. When a usable one exists, a tinted **Update v0.1.27** chip appears at the left of the header's action cluster; clicking it opens a small menu:

- **macOS / Linux** — *Copy update command* puts the `install.sh` one-liner on the clipboard (the chip's arrow briefly becomes a checkmark), plus *View release on GitHub* for the notes.
- **Windows** — *Download from GitHub* opens the release page, which carries the installer.

*Dismiss for this session* hides the chip until the next launch. Nothing installs itself and nothing blocks work — the app never restarts or interrupts you.

## Keyboard surface

The table below is the Tauri client's; its full list lives in [HelpOverlay.svelte](apps/tauri-app/src/lib/views/HelpOverlay.svelte). The composer's `Ctrl/Cmd + Enter` and `Ctrl/Cmd + G` are bound to the window and fire whether or not the composer is focused — a shortcut you must first click into the message to use is one nobody reaches mid-sentence — but only on the Changes tab and only with no dialog open, since a dialog's question is the one on screen and `Ctrl/Cmd + Enter` meaning "commit" would answer something else. `Ctrl/Cmd + P` (push) is likewise bound to the window with no focus gate, so it fires while typing. Every other window-level shortcut is suppressed while a text input or textarea has focus, so they never interfere with the composer. `?` is the only shortcut with no modifier.

The embedded terminal is not a text field but a shell, and it owns its keys: while it has focus, every app shortcut steps aside — `Ctrl+P` is readline's previous-history, `Ctrl+R` its reverse search, `Escape` vim's normal mode — and the *only* chord that still reaches the app is the terminal toggle itself, so the panel can always be closed from inside it. macOS has no such contention to resolve: app chords are ⌘ and the shell's are ⌃, and the native client binds its actions as key equivalents on menu items and buttons, which fire regardless of what holds focus.

| `Ctrl/Cmd + G` | Generate commit message with AI | Global on the Changes tab, no dialog open |
| `Ctrl/Cmd + P` | Push to remote (or Publish branch when it has no upstream / Publish repo when there's no remote) | Global, except in the terminal |
| `Ctrl/Cmd + R` | Refresh status | Global, no input focused |
| `Ctrl/Cmd + L` | Toggle Changes / History tab | Global, no input focused |
| `Ctrl/Cmd + B` | Open branch picker | Global, no input focused |
| `Ctrl/Cmd + ,` | Open Settings | Global, no input focused |
| `Ctrl/Cmd` + `` ` `` | Toggle terminal (collapsed ↔ expanded) | Global, no input focused — **including from inside the terminal**, the one chord the shell doesn't get |

| `Space` | Toggle file selection on focused row | File list focused |

## Persistence model

- `config.toml` in the platform config dir (`~/Library/Application Support/leogit/` on macOS, `~/.config/leogit/` on Linux) — user settings (theme, AI, scan paths, diff prefs, fetch interval).
- `repos-state.json` beside it — last-opened repo (`last_opened_repo`), last clone destination folder (`last_clone_dir`), and the two sort-toggle preferences (`repo_sort_mode`, `clone_sort_mode`).
- `localStorage` (Tauri) — UI splitter sizes (`leogit:sidebarWidth`, `leogit:commitHeight`, `leogit:commitFilesWidth`).
- `UserDefaults` (native) — the commit composer height (`commitComposerHeight`); the sidebar and commit-files widths are per-session for now.
- Per-session in-memory — user-deselected files, active file / commit / diff, terminal PTY ids.

Nothing about the user's code is sent anywhere except the diff that is explicitly passed to the chosen AI provider when **Generate** is clicked.
