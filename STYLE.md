# Frontend Design Principles

leogit's interface is a desktop Git client. The design language is the calm, restrained, system-feeling aesthetic that Apple ships in macOS Tahoe — Finder, Xcode, Settings — built on system blue, semantic surfaces, and the OS font stack. Two themes are supported, Light and Dark.

> **Note on current state.** This document is implemented in the Tauri client: [tauri-app/src/app.css](apps/tauri-app/src/app.css) carries both theme tables token for token, the anti-patterns at the foot of this document appear nowhere in the shipped Svelte, and the re-skin that closed the chrome layer — scrollbars, context menus, the shared backdrop and CTA tokens, the form controls — is written and recorded in [docs/plans/tauri-reskin.md](docs/plans/tauri-reskin.md). What that plan deliberately left is the **shape** of two Settings controls, where this document asks for a toggle and a segmented control and the form still draws a checkbox and a `<select>`: replacing a control is not re-skinning it, and [ROADMAP.md](ROADMAP.md) carries it. Three checks in that plan's §8 still want a Windows and a Linux build to look at. When a component is touched, move it toward this document rather than matching neighbouring code.

> **One look on every platform.** The Tauri client ships on Windows and Linux and wears this same macOS-derived language there: leogit should read as one product, not impersonate each host. The exception is chrome the host OS owns rather than the app — traffic-light window controls, the menu bar, the window frame — which stays whatever the platform draws.

> **The native client is the reference.** The macOS SwiftUI client ([apps/swift-ui-app](apps/swift-ui-app)) reaches this aesthetic by construction rather than by imitation — it uses stock `List`/`Table`/toolbar and the system font stack, so it inherits the macOS 26 look (including Liquid Glass chrome) for free. It deliberately adopts no custom glass or colour treatments: anything it can get from a standard control, it gets from the standard control. Where this document and the native app disagree about a control's look, the native app wins, and this document should be updated to match. The Tauri frontend follows it rather than the two evolving in parallel: where a control's look is in question, the answer is what the native client renders, and the re-skin closing the remaining gaps is [docs/plans/tauri-reskin.md](docs/plans/tauri-reskin.md).

## Intent

If a designer at Apple would not ship it in macOS Settings, Finder, or Xcode, it doesn't belong here. The recurring failure modes we deliberately avoid: GitHub-style colored pill badges on every row, tinted status banners announcing things the user did not ask about (there is exactly one banner in the app, for a repository that has stopped being readable — see *Status indicators*), icon-in-tinted-square section headers, all-caps tracked section labels, chunky pill buttons with leading icons, two-line radio-card pickers with marketing-style descriptions, custom mono fonts (JetBrains Mono, Fira Code) for diff content, accent-color glow shadows. leogit is a tool the user keeps open all day — it should disappear into the OS, not announce itself.

## Typography

- **Font stack:** `-apple-system, BlinkMacSystemFont, "SF Pro Text", "Helvetica Neue", system-ui, sans-serif` for everything chrome-related (sidebar, header, file lists, commit messages, settings, dialogs).
- **Mono stack:** `ui-monospace, "SF Mono", Menlo, Monaco, "Cascadia Mono", monospace` — reserved for diff content, terminal output, SHAs, file paths in diff headers, the Settings scan-path list, and code-shaped strings. Never for labels, captions, button text, or counts.
- **No imported web fonts.** Apple's system stack is doing the work.
- **Default body size: 13px** in app chrome and dense UI. File lists, commit lists, settings and dialog body copy all stay at 13px; a title takes its size from *Section headers*, not from here.
- **Smaller scale:** 11px for compact labels, badges, captions, keyboard-shortcut hints, ahead/behind counts, status footers. 10px for SHA short-hash metadata. 12px for secondary lines (commit author/date under a summary).
- **Diff content: 12–13px mono**, the same scale as the rest of the chrome — don't blow it up.
- **Weights:** regular for body, medium (500) for labels/active states/file names with changes, semibold (600) for headings and the active tab. Avoid bold (700+). The one exception is the **single-letter status plate** in the file list (see *File list*), 10px mono at 700: the native `FileStatusBadge` sets it there (`apps/swift-ui-app/Sources/LeoGit/Design/FileStatusStyle.swift`), and a lone letter carrying a file's whole status out of an 18×18 tint plate is the one place the extra weight earns itself. Nothing else takes it — not a heading, not a count, not a label.
- **No letter-spacing on lowercase text.** Reserve `tracking-wider` for nothing — not even section labels in Settings.
- **Tabular numerics** for any column of digits: ahead/behind counts, line numbers in the diff gutter, commit dates, file change counts, `+N -N` deltas. They must align across rows.

### Usage rules

- Tokens carry semantic meaning. Use `--text-muted` for "secondary information", not "this gray". Reach for hex only inside the theme definition.
- **The accent is reserved for affordances the user can act on**: primary CTA fill ("Commit", "Create Branch"), active tab indicator, focus ring, the selected file in the file list. Never use accent as decoration — no accent borders on the sidebar, no accent text in headings.
- **Status colors are reserved for status.** Don't tint a "Delete branch" button red unless the action is destructive *and* unrecoverable (force push, branch delete with unmerged commits, discard changes). A regular "Delete" button is just a secondary button.
- **Diff add/remove backgrounds are the exception** to the "no tinted backgrounds" rule. Changed-line tinting is information, not decoration. Keep the alpha low (≤12%) so the line stays readable; the foreground color of the `+`/`-` marker carries most of the signal.
- Frosted-glass / `backdrop-filter` effects: skip everywhere. Tauri windows are opaque; the effect is inert and just adds GPU cost.

## Spacing, radii, focus

- **Radius scale:** 6px for inputs, buttons, dropdown items, file rows when selected; 7px for context-menu items; 10px for modals and the branch picker; 12px for the app icon and for the context menu itself. Avoid larger than 12px in chrome — corners shouldn't shout. The two menu radii are a measurement rather than a choice: a macOS 26 `NSMenu` is 12pt at the window with a 7pt highlight inside it, and the Tauri menu reproduces that pair ([docs/plans/tauri-reskin.md](docs/plans/tauri-reskin.md) §6.2 tabulates every menu metric and where it was read from).

  The shipped **app icon** is the branch-graph mark on a dark ground: three nodes and two edges, the diverge-and-merge shape the whole app is about, in the blue→violet gradient. Both clients carry it. The native one authors it in Icon Composer (`apps/swift-ui-app/Resources/AppIcon.icon`), so macOS 26 applies its own rounding, shadow and specular pass — the squircle is the system's, not ours, and the source art must therefore stay a flat full-bleed square with no baked-in corner or shadow of its own.
- **Padding for controls:** ~4×8px (inputs), ~3×12px (buttons), ~6×10px (dropdown items). System-native controls are surprisingly tight.
- **Row height in dense lists:** ~22–24px effective. Vertical padding of 4px with 13px text matches macOS Finder list view. This applies to the file list and the branch list. The commit list is the deliberate exception — its rows are 50px because each commit stacks a summary line and an author/date line (see Commit list).
- **Pane gutters:** 1px borders, never wider. The sidebar/content separator and tab-bar underline are both 1px `--border-inactive`. No 2px divider, no double rule. A resize handle's *grab zone* may be wider (~7px) — its rule stays 1px.
- **The window never scrolls.** `html`/`body`/`#app` are locked to the viewport (`height: 100%`, `overflow: hidden`, `overscroll-behavior: none`) so only inner panes scroll and a trackpad drag at an edge can't rubber-band the whole app. New top-level layout must fit the viewport, not extend it.
- **Scrollbars are one app-wide rule, neutral and unobtrusive.** `scrollbar-width: thin` with `scrollbar-color: var(--border-strong) transparent` set once on `*` ([app.css](apps/tauri-app/src/app.css)), so every scrolling pane shows the same neutral thumb over an empty track in both themes. Width is the engine's: `thin` is a real thickness on Chromium and is ignored by WebKitGTK's Adwaita theme, which honours the colour at GTK's own width. Both properties stay — each is the one an engine actually renders. There is no `::-webkit-scrollbar` block anywhere in the client and none may be added: while either standard property is set the pseudo-elements are inert, so a block can only mislead, and if both were ever dropped it would turn into a custom scrollbar, which is defined never to be an overlay one and would cost every pane a reserved column.
- **The terminal is the one surface this rule does not reach, and that is xterm's doing rather than a choice.** `@xterm/xterm` draws its own scrollbar in JS — a VS Code scrollable element built from `<div>`s — so no CSS scrollbar property applies to it. It is an auto-fading overlay slider, which is the right behaviour, at xterm's own width and at a colour it derives from the terminal foreground; `ITheme`'s `scrollbarSlider*` keys are where that would be overridden if the difference ever stopped being acceptable. `FRONTEND.md` §8 records it.
- **Whether the scroller floats over the content or takes a column from it is the engine's to give, not CSS's.** `scrollbar-width` is `auto | thin | none` and has never had an `overlay`; no property anywhere asks for the behaviour. So it is settled by the host engine, and by the embedder's own switch where one is offered — never by this document. **Overlay is the target on every platform**, because it is what the reference does: macOS draws overlay scrollbars by default, so the native client gets it by using stock scroll views and styling nothing, and WebKitGTK paints them by default, so Linux gets it free. Windows is the one platform that has to be asked, and it is asked where such a switch belongs — `"scrollBarStyle": "fluentOverlay"` on the window in [tauri.conf.json](apps/tauri-app/src-tauri/tauri.conf.json), not in this stylesheet's vocabulary. Where a platform will not give it, that is an intentional divergence for `FRONTEND.md` §8 to record — never a reason to design both platforms down to the one that can't float. The layout corollary: a reserved gutter (`scrollbar-gutter: stable`) is inert wherever scrollbars overlay, so it may narrow a column but must never be what a column's width depends on — which also makes it the right thing to leave in place, since it costs nothing under overlay and is the fallback for a host that quietly declines it.
- **Focus ring:** `outline: none` with `box-shadow: 0 0 0 2px var(--cursor-bg)` — the accent at low alpha (~0.2) — set once in [app.css](apps/tauri-app/src/app.css) for buttons and fields. A field also swaps its border to `var(--border-active)`, and against a filled row it is that solid edge rather than the halo that makes the ring read: at ~0.2 alpha the halo is a wash, so it softens an indicator but cannot be the whole of one. No glowing shadows, no `0 0 20px` halos.
- **A checkbox or radio takes an `outline` instead**, at the accent's full strength with `outline-offset: 2px`, set once in [app.css](apps/tauri-app/src/app.css) beside the shape itself. Neither half of the ring above survives on one. The border half is unavailable outright: neither engine lets an author border reach a checkbox, and unlike a text field a checkbox cannot be styled off the native path to escape that — both engines discard the declaration rather than honour it. The halo half is worse than unavailable, because it is *one-sided*: Chromium paints an author `box-shadow` on a native checkbox and WebKit deletes it, so a halo would be a ring on one platform and nothing on the other, and on Chromium it measures under WCAG 1.4.11's 3:1 anyway. An outline is exempt from both and paints over the control, so it is the only ring these controls can wear on both engines.
- **The colour of a checked box is `accent-color`, and nothing else** — one declaration beside the ring above, never an author `background` or `border`. Both engines read `accent-color` only while they are still painting the control themselves, and a checkbox is a control they never stop painting: an author background or border on one is discarded, not honoured. Sizing it (`width`/`height`) is the exception and works normally.
- **A `<select>` takes `appearance: none`**, and only then the field register above. Half-measures are the trap: an author background or border *without* it leaves the control in a devolved half-native state on both engines, still drawing the engine's own arrow (a different glyph per platform), still reserving that arrow's padding, dropping the focus halo, and — on WebKitGTK — having its `line-height` overwritten, so the control sits shorter than the fields stacked with it. The chevron `appearance: none` removes is drawn back once, as a `::after` on a wrapper (a pseudo-element cannot hang off a `<select>`), from two borders in `--text-secondary` — the same 90° V the header draws for "this opens something", at the affordance weight rather than the label's. **The open list stays the platform's** in both clients: native shows a stock `Picker`, and on Linux the popup is a real GTK widget that consumes no `<option>` styling at all.
- **Shadows:** subtle. `0 4px 12px rgba(0,0,0,0.4)` for popovers/dropdowns/modals in dark; lower-alpha (`0 4px 12px rgba(0,0,0,0.12)`) in light. Never combine shadow + gradient.

## Component patterns

### App chrome / layout

- **Two-column layout**: one permanent split. The left column is the **sidebar** — the tab bar, then the tab's list (changed files or commit history), then on Changes the commit composer — resizable from 280 to 640px and 320 by default; the right column is the **main content** — the tab's detail over the terminal dock. The split sits above the tabs, so switching tabs or emptying a list swaps only what's *inside* each column: the divider never moves or disappears, the composer stays on a clean tree, and the diff always keeps the majority of the window. A nested split inside the detail (History's commit files ‖ diff) is the detail's own.
- **The commit composer is resizable from its top edge**: the 1px divider above it is the handle (~7px grab zone, system row-resize pointer on hover). Range 180–600px, default 220, remembered per client. A taller composer is more description, never more chrome — the summary field and the button row keep their height and the description editor absorbs the rest. Both the drag and the rendered height are capped so the list above keeps a floor (~80px) in a short window. **The description editor sets no minimum of its own**: the composer's 180px minimum is the one floor, and a second floor inside it can only disagree — an editor that refuses to shrink overflows its slot and paints over whatever the composer puts below it.
- Sidebar background: `--bg-secondary`. Main content background: `--bg-primary`. The 1px right border on the sidebar is `--border-inactive`.
- **Terminal pane** docks at the bottom of the main content — under the diff, never under the sidebar — the emulator 280px tall with its header strip above that, separated by a 1px border. Its own background can stay slightly darker than `--bg-primary` (use `#000` or `--bg-primary` — never an arbitrary off-color).
- **The where-am-I controls lead, the one action trails.** Repo name and branch sit at the leading edge; the trailing edge carries a single **adaptive sync button** whose face shows Fetch, Pull, Push, Publish branch, or Publish depending on where the branch stands relative to its remote, GitHub-Desktop style. Both clients are built this way — the native window toolbar and the Tauri header strip are the same control in each platform's own shape, the Tauri one additionally carrying Settings and Help icons after it. No separate refresh button in either: the status poll keeps the view current and a forced reload belongs on a key equivalent, not a button. Keep the strip ~36–40px tall.
- **The pending counts sit with the button, and where is a platform answer.** In Tauri they are capsules on its trailing edge; in the native toolbar they are plain `↑N ↓N` text immediately left of it, because macOS renders a toolbar control's label as text and icon alone and no custom view can ride the face. Both show *both* directions whenever they are non-zero: with a single control the proposed action's number alone would hide the other half of a diverged branch, so each figure carries its own arrow rather than borrowing the face's meaning. A chevron beside the face only where it adds something the face doesn't say.

### Tab bar (Changes / History)

- Plain text tabs, left-aligned, with a 2px accent underline under the active tab. No filled pill backgrounds, no rounded corners on tabs.
- Active tab: 13px semibold `--text-primary` + accent underline. Inactive: 13px regular `--text-muted`. Hover on inactive: `--text-secondary`.
- The whole tab bar sits on `--bg-secondary` with a 1px bottom border in `--border-inactive`. It is the top of the sidebar column, so it spans the sidebar only — never the main content.

### File list (staging)

- One row per changed file. 22–24px row height, 4px vertical padding, 12px horizontal padding.
- **The list's header row is a select-all checkbox and a count, and the count is "3 of 12 files included"** — how many of the committable files are going into the commit, over how many there are. Not "12 changed files": that restates the tab's own pill and answers a question the visible list already answers, while the number the user is about to act on goes unsaid. A dirty submodule is in neither figure, since it can never be staged from the parent. With no changes the header isn't drawn at all — "0 of 0 files included" is a sentence about nothing, and the empty-list line takes the slot instead. **The checkbox is tri-state**: on when every committable file is in, off when none is, and mixed otherwise. A two-state one would read "off" over a list that is mostly on, and this is the control people use to answer *what is going in?* at a glance.
- **The first changed file opens itself.** Arriving at the Changes tab with files listed and an empty diff pane makes the most common next action a click nobody should have to make. The list re-seats on the same two conditions and no others: nothing is open, or what was open has left the working tree. A file the user chose is never overridden, and a tick that only changes a file's content or status is not a re-seat — the trigger is the *set of paths* changing.
- Layout: `[checkbox] [status marker] [path]` — checkbox for staging, single-character status marker in the appropriate status color, then the repo-relative path with the filename in `--text-primary` and the directory muted. **Medium weight on the filename is the inclusion cue**, and the only one: a row going into the next commit reads a shade heavier than one that isn't, without spending a second column on a fact the checkbox beside it already carries. The row carries **no per-file line counts**: `FileEntry` has no additions/deletions to render, and `+N -N` totals belong to the commit detail card, where they are per commit.
- **Status letters** are git's own porcelain vocabulary: `A` added, `M` modified, `D` deleted, `R` renamed, `U` conflicted ("unmerged" is git's word for it). Neither client writes its own set — both read `file_status_styles` from core, so they cannot drift apart again, which is exactly what happened to the conflicted glyph.
- **Conflicted gets its own hue**, `--status-purple`, not the red that already means Deleted. A glance down the list has to separate "you deleted this" from "git couldn't merge this": opposite actions, and only one of them blocks the commit. Colour is the one part of a status's presentation each platform resolves itself, against its own palette. **The same hue marks the merge itself**, on the branch control's `· merging` suffix — an unfinished merge and the files it left conflicted are one state, and the suffix is otherwise the easiest thing on the toolbar to miss, being the first run a narrowing toolbar clips. One token, named once per client, so the two places a merge shows cannot drift apart.
- **Status as a single colored letter on a soft tint plate.** An 18×18 rounded-rect plate tinted at 15% of the status color, the letter centered in it — the native `FileStatusBadge` look, and the shared target. No full-word chips (`[Modified]`), no rounded-full outlines: the letter carries the meaning; the plate only gives it a consistent footprint in dense rows.
- Hover row: `--surface-hover` tint, nothing more. No left-edge accent bar, no scale transform.
- Selected (active diff) row: `--bg-tertiary` background, 6px radius, no border. **Selection is a set** — rows extend by shift-click and by shift-arrow, because discard acts on all of them and Space toggles all of them — so a multi-row highlight gets the lighter `--surface-hover` tint and the one row whose diff is showing keeps `--bg-tertiary`. Selection state, not staging state, gets the emphasis.
- Checkbox: native-feeling square, 14px, accent fill when checked. Mixed-state (some hunks staged) uses an em-dash glyph, not a "minus" pill.
- **Nested repos & submodules** swap the status letter for a ↪ link glyph: blue `--status-blue` for an embedded repo (commits as a gitlink), muted `--text-muted` for a **dirty submodule** that can't be staged from the parent. The dirty submodule also mutes its filename and **disables its checkbox** (40% opacity, `not-allowed` cursor) with a tooltip explaining the change must be committed inside the submodule — the same "inactive but still selectable to view" treatment a read-only row gets. Its diff pane shows a centered "Submodule changes" message rather than a raw subproject-commit line.
- **Path truncation prefers the filename.** When a row is too narrow, the muted directory shrinks to a trailing `…/` bridge but never below a first-letter `b…/` hint, so a nested file can't be mistaken for a root file; the bright filename middle-truncates only once the hint plus the full filename can't fit. Directory characters are never styled as filename or vice versa.
- **Renames** render `[from] → [to]` where both sides share the same filename-first truncation so a deep `from` path can't crowd the `to` out of view. The `from` side is fully muted (filename included); the `to` side is the normal filename treatment. Both flex to equal width.

### Diff viewer

- Two-column gutter (old line number, new line number), then content. Gutter numbers in 11px mono `--text-muted` with tabular nums. Right-align within the gutter.
- Add lines: `--diff-add-bg` row background + `+` prefix in `--status-green`. Remove lines: `--diff-remove-bg` + `−` in `--status-red`. Context lines: no background, prefix is a single space.
- Hunk headers (`@@ -X,Y +A,B @@`): full-width subtle band at `--bg-secondary`, mono text in `--text-muted`. No accent color. One blank line of breathing room before each hunk. **It is a band, not a button** — its text selects with the rest of the diff and it takes no focus ring and no tab stop, unless per-hunk staging is actually wired, in which case it becomes a control and says so with the pointer. Dressing an unwired affordance as a control costs a tab stop per hunk down a long diff and takes the text out of a drag-select, for an action that does nothing.
- **The file header names the diff below it, and a rename is two names.** A renamed file reads `[from] → [to]` under its own filename, both sides muted at caption size and each truncated from the head so the filename that identifies it survives — the file list's rule (*Changed-file list* above), applied where the header would otherwise show only the directory. Rendering the destination alone makes a rename read as an add and loses the one fact that matters about it.
- The `+N` / `−N` totals in the file header use the same glyphs as the row prefixes — `+` and U+2212, never a hyphen — so the header and the gutter read as one vocabulary. A zero side is omitted rather than shown as `+0`: on a binary file or a pure deletion it is noise, and "no additions" is what the absent figure already says.
- **The gutter and the prefix are chrome, not content**: both sit out of the text selection, so dragging across a diff puts the file's own lines on the clipboard and not the line numbers and `+`/`−` glyphs the viewer drew. Selectability is granted to the content, never to the row — a rule stated the other way round leaves it depending on where a drag happened to begin.
- **The gutter is the line handle; the content is the text handle.** Clicking a line number picks that line out, ⇧-click extends the run, and right-clicking the gutter offers the copy; dragging through the code selects characters **within that one line**, which is as far as a native text selection reaches here. Two surfaces, so neither gesture can reach the other's target, and each says what it is: numbers address lines, code addresses text. Selecting more than one line is a thing the reader asks for rather than drags out, and that is the platform's limit, not a preference. Where both could answer a Copy, the run wins — it is a full-row wash, and a visible selection Copy ignored would read as broken — and Escape gives it up. The gutter's whole column is the target, not the digits, and it carries a tooltip naming the gesture, which is the only thing that makes an invisible affordance findable.
- **A slow load dims the diff; it never blanks it.** Under ~150 ms the swap is silent. Past it, what is on screen dims and a spinner sits near the top of the pane — near, not centred, since the rows underneath are what is being read and a tall pane's middle can be below the fold. What is showing is still the truth about the file the user was reading; blanking it throws away the rendered rows, their colouring and the scroll position on every slow load, including the ones that come back identical.
- **A failed read states itself in the pane, in the diff's own place**, with the stale diff cleared: the title, then git's words as selectable mono on `--bg-secondary`. Not the failure strip (which is for the two conditions named under *Status indicators*) and not a modal — nothing is blocked, the repository is still readable behind it, and re-selecting the row is the retry.
- **Unified ⇄ side-by-side lives in the diff's own header**, at its trailing edge after the `+N` / `−N` totals — the arrangement belongs to the diff you are reading, not to a settings window you go and find. Two states, so two segments rather than one glyph that toggles: a control showing only the layout you are already in leaves the reader working out whether the icon is where they are or where they would go. The treatment is the *Segmented controls* rule under **Forms** below, at icon size. It disappears on a binary file, which has no lines to arrange.
- Side-by-side mode: same row heights, same colors, just split. A single 1px vertical `--border-inactive` between panes. Each side carries its own gutter, prefix and row tint, so a delete and the add it was paired with are tinted independently; the side with no counterpart is a **filler cell** washed in `--surface-hover` — a wash, not a tint, so it reads as "nothing on this side" rather than as a fourth kind of change. Hunk headers span both columns, since they describe the whole hunk. Cells stretch to the taller side so the two columns stay row-aligned when one of them wraps.
- Syntax highlighting: muted theme. The highlighter's accent should not compete with the add/remove background. Comments at ~`--text-muted` alpha, keywords at full `--text-primary`, strings/numbers slightly tinted but never saturated. The diff color is the primary signal; syntax is secondary.
- Markdown / prose diffs lean on **weight and style, not saturation** — headings bold, bold/italic/strikethrough carry their real font styling, links underlined, blockquotes muted italic. Colors stay in the same restrained Primer range as code tokens (`--syn-heading`, `--syn-link`, `--syn-raw`, `--syn-quote`), so a `.md` diff reads like the rendered document without shouting over the add/remove tint.
- **A selected line is washed, not repainted.** The run picked out in the gutter takes the system accent at low alpha *over* the add/remove tint and under the text, so a selected added line still reads as added and keeps its syntax colour — a selection is not a fourth kind of diff row. The wash is continuous through a run: the `@@` band and the no-newline marker have no line number to click, but a run reaches over them, so they wash too rather than cutting a gap through the highlight. The band is copied with the run and the marker is not — it is git's note *about* a line rather than a line — which is a difference worth having in the clipboard and not worth drawing a hole for. Side by side, the wash marks every cell whose line the copy will contain — so a run taken down one column also marks its counterparts in the other, which is the honest thing for a highlight that stands for a clipboard to do. When per-line staging lands it needs a control of its own (a checkbox, a prefix affordance), not a second wash — two washes over the same rows cannot be told apart.

### Commit list (History)

- Two-line rows, 50px tall (taller than the 22–24px file/branch rows because each commit needs a summary line and a metadata line). One commit per row.
- Layout, stacked:
  - Line 1 — `[summary] ········ [tag pill] [↑ push indicator]`. The summary grows to fill the row and ellipsizes; indicators are right-aligned. Tag pill: `--badge-bg` / `--badge-fg`, 5px radius, 10.5px mono; a `+N` companion pill when a commit has multiple tags. **Neutral, not accented** — it shares the unpushed arrow's plate, fill and radius so the row's indicators read as one cluster. An accent here made a tag the loudest thing in the row and left the one indicator that actually asks something of the user, the unpushed ↑, as the quieter of the two.
  - Line 2 — `[author] · [relative date]` in 11.5px `--text-muted`, tabular nums on the date. The author ellipsizes first; the date never truncates.
- No SHA in the row — it's copied via the right-click menu's "Copy SHA" and shown in the detail card.
- Selected row: `--bg-tertiary`, 6px radius. Hover: `--surface-hover`.
- The right pane (commit detail + changed files) gets its own thin 1px left border. Below the detail card the geometry matches the changes view: changed-file list on the left, per-file diff on the right, the file column independently resizable — and narrower than the outer column (~240px, capped ~360px), since these rows carry only a path and this diff should dominate its split too.
- **The detail card shows the message once.** The body is `git log`'s own `%b`, which already ends in the commit's trailers, so a separate trailer list under it is the same lines a second time — stripped of the paragraph they belong to, and looking like data the app added. Whatever the commit says, in the shape it says it.

### Commit message composer

- Lives at the bottom of the sidebar. Two stacked fields: a single-line title input (72-char soft limit, shown as a 11px `--text-muted` counter that flips to `--status-yellow` past the limit — inside the field's trailing edge where the platform's field can reserve room for it, immediately beside the field where it can't). The limit is advisory: nothing is ever truncated, since a silent hard cap chops pasted and AI-generated summaries with no warning at all and a multi-line description textarea. The title overflows horizontally with no scrollbar; a wheel/trackpad delta is mapped onto `scrollLeft` so a long summary can be swiped through (native single-line inputs only scroll via the caret).
- Inputs use `--bg-primary` (recessed against the `--bg-secondary` sidebar), 1px `--border-strong`, 6px radius, 2px accent focus ring.
- **No label above the inputs.** The placeholder ("Summary", "Description") is enough. Reserve labels for forms with mixed field types.
- Action row at the bottom: `[Commit]` primary (accent fill, right-aligned), `[AI ✨]` ghost-icon button to its left if AI commit messages are enabled. No leading icon on Commit itself.
- **Description is *not* monospace.** The current implementation may render it in mono — switch it to the system font. Reserve mono for content that benefits from fixed-width alignment.
- **Amend notice** — while the composer is rewriting the last commit, a caption-sized band sits above the summary field: "Your changes will modify your **most recent commit**." with a link-styled *Stop Amending* on the trailing edge. Marked by a 2px `--status-yellow` rule on its leading edge, not a filled block — the composer is already a dense stack of bordered fields, and a tinted panel here reads as another one. It never names the commit: the message it seeded is in the fields directly below.
- **Status strip** — everything that went wrong sits in **one** caption-sized block between the description and the action row, marked by a 2px `--status-red` leading rule (the amend notice's shape, in the failure colour) rather than by a filled panel or by loose lines floating in the stack. Up to two rows, in this order: the failure of the last attempt in `--status-red`, and the standing reason an action is unavailable in `--text-secondary` — a state, not an attempt, so never in red. Long provider text wraps rather than widening the composer.
- **A remedy sits immediately after the sentence that explains it**, on the same row, left-aligned and baseline-aligned, **one word space away (~4px) — not a gutter**: the two are one sentence, and a gap wide enough to read as a column break undoes that. Never pushed to the trailing edge, which separates the action from its reason by the whole width of the sidebar. It reads as a sentence, and **only the part that acts is a control**: `Run` is prose at the strip's own size and colour, and the command alone is clickable — its own `--bg-elevated` chip, 4px radius, `--font-mono`, `--border-active`, `--surface-hover` + underline on hover, and the link pointer natively. The command is spelled out because the app is about to type exactly that into the user's shell. **No border and no button chrome around the phrase**: wrapping `Run <command>` in one bordered control made the whole thing read as an oversized button and hid which half was actually clickable.
- **An inline label never sets its own size.** Inherit the strip's, and step monospace down (~0.92em, or 9.5pt against macOS's 10pt `.caption`) so the parts of a mixed run match — mono renders visually larger than the UI face at the same value. Natively that means stating the font: `.controlSize(.small)` sets a button's own metric and silently overrides the caption around it.
- **A remedy replaces the failure it was read out of** rather than stacking under it — both describe one state and the remedy is the actionable half, so the raw provider wording moves to the row's tooltip. Failures from *other* actions keep their own row: a commit failure stays visible while the AI provider is separately blocked.

### Context menus

- **The native client takes the system menu; the Tauri client draws its own to the same metrics.** Natively a row context menu is a **stock system menu** — plain items, `Divider()` between groups, the destructive role on the one item that destroys work, nothing hand-drawn or re-themed — the same rule that governs the toolbar and the terminal's accessory bar. On Windows and Linux the stock menu does not resemble the reference at all: a Windows context menu is a classic win32 `HMENU`, and no theming API exists anywhere in the stack to bring it back, so taking it would put the one control in the window that reads as another app's. There the menu is drawn to AppKit's measurements instead — a reproduction, not a licence to redesign. The rules below govern both.
- **Disable, don't hide.** An action that doesn't apply to this row (reveal a deleted file, amend a commit that isn't HEAD) stays in place greyed out, so the menu has one shape and its items keep one position.
- Order runs destructive → repository-changing → copy → hand-off to the OS, separated by dividers, so the item that can lose work is never adjacent to the one people click most.

### Buttons

- **Primary action:** solid accent fill (`--border-active`), white text, no leading icon, ~3×12 padding, 6px radius. One per dialog/section: "Commit", "Create branch", "Merge", "Confirm force push".
- **Secondary action:** `--bg-elevated` background + 1px `--border-strong`, no fill. Use for cancel, "Browse…", "Open in Finder…".
- **Ghost / tertiary:** transparent, text-only, `--surface-hover` on hover. Use for in-row icon buttons (the X to close the terminal, the AI sparkle), inline links.
- **Destructive:** secondary button styling with `--status-red` text. Reserve for genuinely unrecoverable actions (force push, branch delete with unmerged work, discard hunk). A plain "Delete branch" with safe local-only deletion stays secondary.
- **Order in dialogs:** Cancel on the left, primary on the right, right-aligned at the bottom. The reverse reads as web app.
- **Ellipsis convention:** trailing `…` for actions that open further UI ("Browse…", "Open repo…", "Switch branch…").

### Forms (Settings)

- **No Save button.** Settings apply as they are changed and the one footer button closes the window, so nothing may look like a pending edit: no dirty marks, no "unsaved changes" state, no confirm-on-close.
- A rejected write is one 12px `--status-red` line at the top of the body, above the sections, and the control that raised it goes back to what is on disk. It never becomes a modal — a window stacked over the form covers the field it is talking about.
- Label-on-left layout with right-aligned labels at a fixed column width (~140px for Settings — slightly wider than LeoSync's 96–112px because leogit's labels run longer: "Auto-fetch interval", "Syntax highlighting"). Inputs flex into the remaining width.
- Inputs use `--bg-primary` (recessed against `--bg-secondary` settings container), 1px `--border-strong`, 6px radius, 2px accent focus ring (no glow).
- Group related fields without dividers — vertical rhythm carries the structure. Use a single section header + thin 1px `--border-inactive` rule only between top-level sections, in one order across both clients: Appearance / Git / Diff / Repository Discovery / Terminal / AI Commit Messages.
- **A section footer says what the section applies to, and when** — 11px `--text-muted` aligned to the control column, under the last control of its section ("Applies to the open diff immediately."). Per *section*, not per control: the scope of "immediately" is the group, not any one checkbox in it, and both clients carry the same sentences.
- Don't use floating labels, helper text under every input, or asterisks for required fields. A per-control hint is allowed only where an option's scope isn't self-evident and the section footer can't carry it — never as a routine caption.
- **A destructive text field locks behind Edit ▸ Done** instead of applying as you type: read-only on `--bg-secondary` with an **Edit** button below it, which becomes **Done**, and only Done writes. Scan paths are the case this exists for — a half-typed line is a different folder, and the list decides which repositories the app can see at all; being paths, they are set in the mono stack, where a stray space or a doubled slash is visible. Leaving mid-edit discards the draft; no confirmation anywhere in the cycle.
- **Toggles** for booleans (auto-fetch, hide whitespace, syntax highlighting): flat solid accent fill when on, white knob, no gradient.
- **Segmented controls** for 2–4 mutually exclusive options (AI provider: Claude/Ollama; theme: Light/Dark; the diff viewer's unified ⇄ side-by-side, which is the one that lives outside this form). A single rounded container with sub-buttons; selected segment gets `--bg-elevated` fill + `--text-primary`, unselected segments stay transparent + `--text-muted`.
- Numeric settings (fetch interval, tab size, scan depth, the AI timeouts) are plain fields with tabular nums and **no stepper arrows** — a spinner is a second way to change a value that already has a keyboard, and under instant-apply each click of one is another write. macOS's `Stepper` is the exception the platform earns natively. Show the unit the user thinks in, not the one the wire carries: the fetch interval reads in seconds in both clients and is milliseconds only in `config.toml`.
- The two control shapes above are the target and the native form already has them (`Toggle`, `Picker`). The Tauri form draws a checkbox and a `<select>` instead, both styled to this document's own register — accent-filled, with the focus ring under *Spacing, radii, focus* — because reaching a toggle or a segmented control there means **replacing** the control rather than re-skinning it, which is a change of behaviour and keyboard semantics and so sits outside the re-skin ([docs/plans/tauri-reskin.md](docs/plans/tauri-reskin.md) §6.5 records the reasoning; [ROADMAP.md](ROADMAP.md) tracks the shape change itself). The three binary selects are the candidates when it happens — theme, and the AI provider in both places — and the diff header's unified ⇄ side-by-side control is the segmented pattern already built. Everything else in this section is what both forms do today.

### Section headers

- Plain text. No icon-in-tinted-square. No subtitle below the title unless it adds non-obvious information.
- **Three registers, picked by what the title sits on top of** — a surface, a pane's content, or an empty pane. One size for all three flattens a hierarchy the native client actually draws.
  - **15px semibold** — sheet, dialog and failure titles: "Clone Repository", "Discard Changes?", "Force Push with Lease?", the error sheet's *Error*. Native gets this from `.title3.weight(.semibold)`, which macOS draws at 15pt.
  - **13px semibold** — detail-pane headings (the commit summary on the History detail card, the filename in the diff header) and the section labels in Settings. Native takes `.headline` for the panes and lets a grouped `Form` size its own section headers; the web client has no `Form` to inherit from, so it sets both itself.
  - **System-sized** — the title of a **pane-level** empty state, which is never given a size at all: native draws these with a stock `ContentUnavailableView` sized for a pane rather than for a row, and the web client matches it at 15px. A *list's* empty line is a different thing entirely — one faint centred line, see *Empty states*.
- If a section needs a description, render it once at the top with `--text-muted`, not as a subtitle under every header.

### Modals / dialogs

- Small. 360–420px width. Tight padding (16–20px). Header + body, no card-within-card chrome.
- Backdrop: `rgba(0,0,0,0.3)` light, `rgba(0,0,0,0.5)` dark. No backdrop blur (skip in the desktop app where opaque windows make the effect inert).
- Close affordance: an overlay that holds a whole surface (Settings, Help) gets a tiny X in its header corner; a confirmation's Cancel button is its own. `Escape` dismisses either. Backdrop click dismisses for non-destructive dialogs (Settings, Help, Branches); destructive ones (Force push, Discard changes, Delete branch, Abort merge) require an explicit button — and none of them dismisses by any route while its operation is still running.
- **`Escape` reaches the frontmost surface only, and never leaks past it.** A confirmation raised from a popover closes itself and leaves the popover standing; one whose operation can't be called off swallows the key rather than letting it dismiss whatever is underneath. That is a property of *when a surface appeared*, not of where the key was pressed, so a dialog declares its own dismissal as it mounts and never reads the keyboard itself.
- **A dialog takes focus when it mounts** — `use:autofocus` on the modal container, or on its first field where it has one — so `Tab` starts inside the dialog rather than walking the page behind it. Suppress the container's focus ring; it is a listening post, not a control.
- **Confirmations that differ only in their words share one component** ([ConfirmDialog.svelte](apps/tauri-app/src/lib/components/ConfirmDialog.svelte)): a title, a body snippet, the verb on the button, the label it wears while the operation runs, and whether it is destructive. It holds itself open under that busy label rather than vanishing on the click — a dialog that disappears leaving nothing behind reads as though nothing happened.
- One concern per modal. Prefer in-page sections (sidebar tabs, settings categories) over spawning a modal.
- **A dialog running an uncancellable operation freezes its inputs with one `<fieldset disabled>`, not a `disabled` per control.** Per-control flags are a list that a later control forgets to join — which is how the Clone dialog stayed editable mid-clone and let a new selection rewrite the "Clones into…" preview to a path nothing was being written to. Group the controls that choose *what* the operation acts on; reset the fieldset to `border: none; margin: 0; padding: 0; min-inline-size: 0` (its default `min-content` inline size refuses to shrink and would widen the dialog), and dim it ~0.55 so "not yet" is visible rather than discovered by clicking. **Progress and errors stay outside** it: the bar reporting the operation must not be dimmed by the operation.
- **Error modal** ([ErrorModal.svelte](apps/tauri-app/src/lib/components/ErrorModal.svelte)): title in `--status-red` semibold, git's text in the body as selectable mono on `--bg-secondary`, and a right-aligned footer of **[Retry] [Dismiss]** — Retry secondary, Dismiss primary, and Retry present only when the failed operation has a second attempt worth offering. No icon-in-tinted-square next to the title. Retry closes the modal before re-running: leaving the first failure on screen would make a successful retry look like nothing happened.

### Branch picker

- Popover anchored to the branch button in the header. ~280–320px wide.
- Top: a single search input (placeholder "Filter branches…"). No label.
- List below: 22–24px rows, branch name in `--text-primary`, remote rows in `--text-muted`, current branch marked with a small accent dot to the left of the name — one marker, never a dot *and* a bar. Section headings ("Local Branches", "Remote Branches") use the muted 11px label treatment, and the keyboard cursor is the repo picker's inset accent ring, so it composes with the current row's fill rather than replacing it.
- **The footer is the action list, not one button**: full-width left-aligned ghost rows at the same 24px as the list — "New branch…", "Merge into “*current*”…", "Abort merge…", "Delete branch…", each with a trailing `…` because each opens something. It lives outside the scrolling list so it survives an empty one, which is exactly when "New branch…" is what you wanted. An action that doesn't apply stays in place disabled with a `title` saying why; **Abort merge is the one exception and is hidden outside a merge** — it has no meaning in any other repository, where a permanently greyed row would be pure noise.
- **An action that needs a branch borrows the list instead of opening a second one.** Merge and Delete put the popover into a picking mode: a header row with a back chevron states the question, the rows narrow to the candidates, and the destructive one tints its rows `--status-red` so the list itself says what is about to happen to the row you click. The filter, the cursor and the row rendering are the browse mode's, written once.
- Right-click a row for the same actions (destructive first behind a divider, per *Context menus*). It is the pointer's short path, not the only route — every action is reachable from the footer by keyboard.

### Repo pickers (switcher popover + startup modal)

- **The two are one component family**, and anything shown in both is shared code, not a matched pair of copies. They drifted before — twice, on the empty state and on the row labels, and the second one broke search: a list that displays `owner/name` and searches only basenames cannot find what it is showing. So the empty state ([RepoListEmptyState.svelte](apps/tauri-app/src/lib/components/RepoListEmptyState.svelte)), the row labels and the footer are the same code in each. The native client goes one step further and makes the two lists literally one view (`RepoPickerList`), parameterized only by how much room it has and whether a repository is already open.
- **A row is named, not pathed.** The remote's repository name where there is one, the folder's name otherwise, ellipsized in the middle; the owning account appears as a muted `owner/` prefix **only** on rows whose name another row shares. It is disambiguation, not decoration — a repo with no remote has no owner to show, and prefixing every row would put the same word down the whole list. The full path lives in the row's tooltip, under the owner-qualified name.
- **The sort toggle is the second control in the filter row**, an icon-only button whose glyph *is* the state label — a clock for recency, A→Z for alphabetical — with the sentence in its tooltip. Same control, same two glyphs as the Clone dialog's; only the tooltip differs, because "recent" means *last opened* here and *last pushed* there.
- **The keyboard cursor is not the pointer's highlight.** Hover is the lighter wash; the cursor reads as a selection (a fill natively, a `--border-active` inset ring on the web), so the row the pointer is resting on and the row Return will act on are never confused for each other.
- **A row that cannot be picked stays visible, dimmed, and says why on hover** — never removed, and never `disabled`/`.disabled(…)`, since a disabled control takes no pointer events and the tooltip explaining it would never appear. That tooltip is the entire reason the row is still on screen.
- **A failed walk is a row above the list, not a screen instead of it.** One caption line under the filter row, hairline beneath: a `--status-yellow` warning triangle, *Couldn't search for repositories.* in `--text-primary`, and a **Retry** link at the trailing edge, disabled while a pass is running (a second click would coalesce into it and look like nothing happened). Git's own reason is the row's tooltip, not its text — it names a scan folder the walk could not read, which is context rather than the headline. Shared by both pickers like the empty state above it.
- **Footer row**, a hairline above it, 8×10px padding: `Clone Repository…` at the trailing edge. A ghost text button at 12px `--text-secondary`, brightening to `--text-primary` on a `--surface-hover` fill, with a trailing `…` because it opens something. Text, not an icon — it is the list's one escape hatch, and it reads better labelled than as a second glyph competing with the sort toggle above it.
- **The footer lives outside the list**, so it survives every empty state. That is the whole point of it — the states where the user most needs a way out are the ones with no rows.
- List rows are 24px, name in `--text-primary` ellipsized, indicators trailing (see *Status indicators*). The scrolling list gets `min-height: 0` so it shrinks instead of pushing the footer out of the popover.

### Terminal

- Background `#000` (or `--bg-primary` in light, but real terminals are dark — `#000` is fine on both themes). Mono font, 12–13px.
- The emulator sits on a small gutter — ~8px horizontal, ~6px vertical — painted the same black, so it reads as part of the terminal. Terminal emulators draw edge to edge, which leaves the first column touching the header strip above and running into the window's rounded bottom corner, where it gets clipped.
- Header strip ~28px on a toolbar material, with a 1px rule above it. It is an **accessory bar** — the recessed scope-bar control class macOS uses for Finder's search scopes and Safari's favourites bar (SwiftUI's `.accessoryBar` button style, at `.controlSize(.small)`). The shell name leads on the left; New Session `+`, the expand/collapse chevron, and the session-killing `✕` sit icon-only on the right, with `✕` disabled while no session exists.
- **Never hand-style the strip's controls.** The accessory bar draws hover, press, and selected states itself; a strip of plain/borderless buttons with a forced secondary foreground renders as inert glyphs that give no feedback on mouse-over, which is exactly what reads as non-native. Same rule as the toolbar: use the system control, don't imitate it.
- **Active shell name** is the label of a button-styled toggle beside a terminal glyph (`apple.terminal` — the current-era symbol, not the older generic `terminal`), so the strip carries the panel's open state the way a scope bar carries a selected scope. It reports what actually launched, which can differ from the configured preference when that shell isn't installed, and reads `Terminal` until a session names itself.
- Icon-only buttons are still built from labels, so every one has a tooltip and an accessibility name. There is no bottom-toolbar placement on macOS (`.bottomBar` is unavailable there), so this strip is hand-assembled by necessity — but out of stock controls.
- **A gesture that needs a modifier says so on hover.** A URL in the scrollback opens on modifier-click, not a plain one, because a plain click belongs to the selection — and an underlined link that does nothing when clicked reads as broken. So hovering names the gesture in the platform's own spelling: a small tooltip, *Follow link (⌘ + click)*, in the UI font over the emulator's mono, positioned on the pointer and pulled back inside the panel at the edges. Sizing and colour follow the app's other chrome (11px, `--bg-secondary` on a `--border-inactive` hairline, 5px radius), not the terminal's palette: it is app chrome standing on a terminal, and should look borrowed rather than emitted.
- **280 means the emulator, not the dock.** The header strip sits on top of that height rather than inside it, in both clients, because what the number is really setting is how many rows the shell gets — and measuring the dock instead quietly spends the strip out of the grid.

### Empty states

- **An empty state that a setting can fix must carry the fix.** "No repositories found" alone is a dead end; name what was searched, then offer the action. Pattern: a plain title in `--text-faint`, an 11px explanatory line inheriting it, the searched values as an 11px mono list in `--text-muted` (paths are data — mono), then a single tertiary button. Left-aligned text would fight the centred modal, so the whole stack stays centred.
- **Say which emptiness this is.** One string for every cause is the failure the pattern above exists to prevent: *still looking* (a small spinner over the title), *nothing found anywhere* (title + what was searched), and *nothing matched your filter* (title alone) are different problems with different fixes. The searched-folders list belongs only to the middle one — the user who typed a query knows the list isn't empty. The fix button belongs to both non-loading states: "none matched" is what you see when the repo you want lives somewhere discovery was never pointed at.
- Don't stack more than one action. The contextual button and the persistent header control are enough; a third route reads as uncertainty about which one works.
- **A sidebar list with no rows shows one faint centred line** (`No changes`, `No commits`), never the icon-and-headline treatment: that is sized for a pane, and the pane-sized story ("The working tree is clean.") is the detail column's to tell. The composer stays put underneath — the placeholder claims exactly the list's slot.
- **A pane's empty state answers the pane's own question, not the list's.** Beside a list that says `No commits`, the detail pane says the repository has no history — not "select a commit", which is an instruction the user cannot follow. "Nothing is selected" and "there is nothing to select" are different states and read as different sentences.
- **An empty state that replaces only part of a pane must still claim the whole pane.** Sized to its own content, it leaves the pane's stack shorter than the slot it sits in, so the layout centres the stack — and a header meant to sit at the top drifts to the middle, where it reads as oversized chrome rather than as a short body. The header stays pinned; the empty state takes the rest and centres inside it. This is what the binary-file and "no textual changes" diff bodies do.

### Repo-less chrome

- The header bar is **the same component** in every phase, not a reduced copy. When no repository is open it simply drops everything that acts on one (repo/branch chips, status area, the sync button) and keeps Settings, Help, and the update chip. Never build a second, simpler header — the two would drift, and the user would notice the app "changing shape" between launch and main view.
- App-level chrome (Settings, Help, update availability) is reachable in *every* phase. A phase that can't be escaped without restarting the app is a bug, not a layout.

### Status indicators

- **Connection / sync status** (ahead/behind): standalone muted text beside the sync action — `↑N ↓N`, tabular numbers, secondary foreground, no background, no border, no capsule. It is status, not a control: it must never look clickable. Hidden entirely when in sync; the spelled-out counts ("2 commits to push") live in a tooltip.
- **Counts in tabs** (the Changes tab): a small stadium pill after the label — 16px tall, ≥18px min-width, 11px medium tabular number, muted foreground on `--badge-bg`. Hidden at zero, never capped. Never a bare parenthesized number — "(12)" in a control face reads as an afterthought, not an indicator. Toolbar action buttons (Pull/Push) carry **no** count: a macOS system toolbar control can't host a custom view, so the counts stand as separate status text beside the button (see *Connection / sync status* above) — don't imitate the system control to smuggle a pill in.
- **Dirty dot (repo switcher rows):** a 6px `--text-muted` circle between the repo name and its `↓/↑` badges, brightening to `--text-secondary` with the row like the badges do. It signals "has uncommitted changes" without a count — the Changes tab carries the number.
- **Update chip:** informational, not an action the user owes us. In the Tauri header, left of the action cluster, it says so by being *tinted* rather than solid: `--status-blue` text on a `color-mix` 12% wash of the same token with a 40% border (20% on hover), sitting a step below Pull/Push in the bar's hierarchy while still reading as new — same 28px height and 6px radius as its neighbours, an up-arrow glyph, no count badge. Natively it is a **stock toolbar control** like the two chips beside it, per the standing rule above: it appears only when there *is* an update, so it is notable without a colour treatment, and a hand-tinted third chip would be the only non-native control in the window. Both rules survive the same way: an up-arrow glyph, and the "copied" confirmation swaps **the glyph** for a checkmark and leaves the label alone — swapping the *text* would resize the control and shove its neighbours sideways for the duration (natively that means `arrow.up.circle` → `checkmark.circle`, which share a footprint). Never a banner, modal, or toast — an update is never urgent enough to take space from the repo.
- **Failure strip (under the header, above the content):** the app's one banner shape, used for exactly two conditions and no others. A single 12px line the full width of the content column, a `--status-yellow` warning triangle, the sentence in `--text-primary` and git's own text after it in 11px mono `--text-muted`, ellipsized (it is data, and the part worth selecting), on a `color-mix` 12% wash of the same token with a bottom hairline. **The two conditions are two lines, not one line showing whichever came first** — they are retired by different things and neither may silence the other; when both stand, the undismissable one is on top.
  - **The repository stopped being readable** — the poll's own. The pane below is showing a snapshot that is no longer true, and a modal would demand dismissal on every tick while a toast would vanish while the problem stayed. **No dismiss control on purpose:** it goes away when the repository comes back, and nothing else should make it go away.
  - **An OS hand-off didn't take** — Finder wouldn't reveal, the browser wouldn't launch. The user asked for something outside the app and it didn't happen; nothing in the repository changed, so taking the window over it is a bigger interruption than the failure. This one **carries a ✕**, because unlike the poll's there is no later success that could retire it.
- **What is not a banner.** A failure of an operation the user is waiting on — a transfer, a branch change, a commit — belongs in the modal, which is what "the thing you asked for did not happen" looks like. Anything merely informational belongs in a chip. The line between the modal and the strip is *is the user waiting on this*, not how bad it is. **A failure raised from inside a dialog stays in that dialog**, under the fields, with everything typed intact: the dialog is already the retry surface, and a modal stacked on top costs two dismissals to change one character. Git's or gh's own text, mono and selectable, capped in height and scrollable.
- **Transfer progress (fetch / push / pull / publish / clone):** progress lives *inside the control that started it* wherever the platform lets it, GitHub-Desktop style — no toasts and no floating progress windows. (A macOS toolbar control renders as text and icon only, so the native client draws the same progress as a strip under the toolbar instead; the rule it keeps is *next to what started it*, not *inside* it.) The sync button gets a full-height `--surface-hover` fill scaled with `transform: scaleX(fraction)` (`transform-origin: left`, 0.3 s ease-out so git's phase jumps glide instead of teleporting); button content layers above via `position: relative`, and the usual `:disabled` dimming is cancelled while the fill shows (the spinner already signals "busy" — graying the progress out would defeat it). **Where there is no percentage to show, the fill sweeps rather than sitting at zero** — a bar frozen at 0% reads as stuck, and fetch and publish never report one (nor does a push until git's first tick). Git's raw progress line renders in the header status area in 11px mono `--text-muted`, ellipsized. The Clone and Publish dialogs use a 4px rounded bar (`--border-active` fill on `--bg-secondary`), determinate for a clone and sweeping for a publish, above the same mono line.

### Icons

- SF Symbols–style line icons at 12–14px in chrome (header buttons, dropdown delete, modal close), 14–16px for standalone toolbar buttons. Stroke icons over filled icons for chrome. Filled icons for status only (the green sync dot, the conflict triangle).
- **Inline SVGs**, not unicode glyphs. `⎇`, `↑`, `↓`, `⟳`, `↻`, `⚙`, `?`, `✕`, `●` and similar TUI-flavored characters render at OS-default weight in whatever font happens to be available, look misaligned in dense rows, and are inconsistent across themes. Hand-rolled SVG paths with `stroke-width="1.4–1.6"` and `stroke-linecap="round"` match the macOS line-icon weight and inherit `currentColor` from the parent button. Reusable patterns currently inlined: branch glyph (header), up/down arrows (the sync button's Pull/Push faces, the count capsules, and the repo rows' ahead/behind), upload-over-baseline (Publish branch) and cloud-up (Publish repo), refresh swirl (the Fetch face, and the same glyph spinning via `@keyframes spin` while any op is in flight), gear (Settings), circled-question (Help), close X (modals + delete), checkmark (copied state), clipboard (copy SHA).
- **Don't put icons in tinted square backgrounds** anywhere — not for section headers, not for the app logo block, not for the AI button.
- **Don't lead buttons with icons** by default. "Commit", "Create branch", "Merge" are text-only. The sync button is the principled exception: the arrow direction *is* the affordance, and it sits next to a count that needs an anchor. Ghost icon-only buttons (close X, gear, sparkle, refresh) are fine — those are *icon* buttons, not icon-led text buttons.

## Anti-patterns (don't ship these)

- GitHub-style colored pill badges on file rows (`[Modified]`, `[Conflict]` in a rounded-full tinted chip). Use the single-letter tint plate instead.
- Gradient mesh / aurora backgrounds anywhere in the app.
- Accent-color glow shadows around buttons, inputs, or cards.
- Icon-in-tinted-rounded-square next to every section title.
- Active state communicated *only* by gradient or glow.
- All-caps `tracking-wider` section labels.
- Helper subtitles under every form input in Settings.
- Two-line "radio card" pickers for theme or AI provider when a segmented control fits.
- Custom mono fonts (JetBrains Mono, Fira Code, etc.) for diff content or terminal output — system mono is fine and faster.
- Backwards button order (primary on the left of Cancel).
- Force-push / Delete-branch buttons styled as full-width destructive banners. A red secondary button inside the dialog is enough.
- Tinted full-row backgrounds in the file list to "color-code" file type or status — the status letter carries the signal.

## Marketing site (future)

leogit currently has no marketing site. When one is built, the same design language applies — same font stack, same color tokens, same restraint — with these adjustments:

- Body copy may scale up to 15–17px on hero/landing sections; chrome-scale elements (download buttons, footer, nav) stay at 13px.
- Section rhythm uses generous vertical padding (64–96px between sections), but components *inside* a section follow the tight scale used in the app.
- Horizontal nav, transparent over hero, switches to a subtle `--bg-secondary` background on scroll. 4–6 nav items max, right-aligned.
- Hero CTA: single primary button (accent fill, "Download for macOS") + a quiet secondary text link ("View on GitHub"). No leading icon, no trailing icon, no glow, no gradient.
- Feature cards: subtle `--surface-hover` fill, no border, no hover lift, no gradient. Numeric or icon up top, 13–15px label below.
- Screenshots of the app are the marketing material. Don't dress them up — let the calm UI speak.
