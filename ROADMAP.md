## Recently completed

- [x] **Cross-client parity, workstream Q — the History pane stops saying things it doesn't know yet, and three dialogs stop lying about what happened.** A repository whose first `git log` was still in flight was being told it had *no commits*, in two places at once; an empty list is equally true of a repository with no history and one that hasn't been read, and only the store can tell those apart, so `RepoStore.historyLoaded` now gates both. The same read clears the previous repository's commits at the moment it publishes the new path, which is what stopped the detail pane loading one repository's sha against another's. Commit dates **re-tick every 10 s** natively as they always have in the Tauri client, gated on the window being visible through the existing scheduling policy rather than a second timer of their own — and both clients now spell out **one vocabulary** (`just now`, `5 minutes ago`, `3 days ago`, `2 years ago`) instead of each delegating to its platform's formatter, which had them rendering the same commit as *yesterday* and as *1 day ago*. Paging asks for the next page five rows early rather than at the very last one, tag chips took the neutral plate the unpushed ↑ beside them already wore, and the list scrolls back to the selected commit after a trip through the Changes tab instead of jumping to the top. **Three confirmations became sheets**, because a `confirmationDialog` dismisses on the click and so can neither say it is still working nor hold what came back: checking out a commit holds itself open saying *Checking out…* (which is also what stops a second checkout racing the first), force push says *Force-pushing…* and keeps a refused lease inside itself, and both keep git's own words where the fields that caused them are still on screen. Underneath all three, a guard that had been answering `nil` for *succeeded* and for *never ran* alike now answers which: it had been dismissing the create-branch sheet on a branch that was never created and reporting merges that never happened, and the same shape sat unnoticed in the sync slot, where the new force-push dialog would have closed reporting a push a background fetch had prevented. Failures that the user is waiting on finally look like the Tauri client's: one sheet carrying git's text monospaced, selectable and scrollable, instead of a system alert that reflowed a rejection into one unselectable paragraph and lost the ref names worth copying. Undo stopped reloading the branch list it cannot have changed, checkout and undo failures moved out of the background strip and into the modal where the rule puts them, and the `· merging` suffix on the branch chip took the conflicted-file colour so the state that changes what half that menu does no longer reads as part of the branch name.

- [x] **Cross-client parity, workstream P (cont.) — copying a diff gives you the file, not the picture of it.** `copy_diff_text` had been sitting in core, the bridge and the Tauri shims with no caller anywhere — the plan's one deliberate dead surface, and the only thing that could close D-15. It has a consumer now. The native diff's **gutter is a line handle**: click a number to pick that line out, ⇧-click to take the run between, right-click for *Copy N Lines* or *Select All Lines*, ⌘C to copy, Escape to drop it. What lands on the clipboard is rebuilt from the parsed diff, so it carries none of what the viewer drew around the code — no line numbers, no `+`/`−`, no side-by-side filler cells — and it keeps the file's real tabs, which the pane has to expand to spaces because SwiftUI `Text` honours no tab stops. Dragging through the code still selects characters and still copies exactly what was dragged over: the two never contend, because the pane claims the Copy command only while a run is picked out and declines it otherwise. `.textSelection` also moved off the row stack onto the content alone, so a drag that begins in the gutter can no longer pull line numbers into a copy — the rule STYLE.md had been stating for a client that didn't follow it. The selection lives in `DiffStore` beside the rows it indexes, and is cleared in the one place those rows are rebuilt, so it can never address lines belonging to a diff that was replaced under it; a layout change moves no line, so the run survives it exactly as the scroll position does. The remaining half is the Tauri client's multi-line copy, which today keeps gutters and prefixes out of a drag-select — the same text for a unified diff, still interleaved for a side-by-side one. Three defects in core turned up on the way and are fixed with it, all of which both clients had been showing: `/dev/null` survived the parse, so a diff header comparing its two sides to spot a rename read every *added* file as `/dev/null → <file>`; `copy_text` emitted `\ No newline at end of file` as though it were a line; and the parser turned every patch's own trailing newline into an empty context row, a blank numbered line at the foot of every diff. The rename arrow now comes from the status entry in both clients, because the diff genuinely cannot answer it — both reads pathspec-limit to the file's current path, so git never pairs it with the deleted counterpart and reports a rename as a plain add.

- [x] **Cross-client parity, workstream P — the diff pane stops reading someone else's file.** Three defects that all came from the pane deriving something from the wrong source. **The reader's place in the file** — switching files landed you at the previous file's scroll offset, often past the end of the new one, because the native viewer had no scroll control at all. `DiffStore` now publishes `rendered`, the identity of the diff *on screen* (its path and, in History, the commit it belongs to), and a bound `ScrollPosition` sends the pane to the top when that moves. Every re-read of the same diff — a layout toggle, a whitespace change, an edit landing from another window, a `HEAD` move — leaves the offset exactly where it was, which is the contract the seamless path exists to keep. The Tauri client's own reset key gained the commit for the same reason: one path in two commits is two different diffs, and stepping through History with a file selected was keeping the offset from the previous commit's version of it. **What the header says** — a renamed file now reads `old → new` under its name in both clients rather than only the destination, which is indistinguishable from an add; the `+N −N` totals show each side only when it is non-zero, so a binary file says nothing instead of `+0 −0`, which described a change as no change at all; and neither is shown while the payload on screen is still the previously open file's, since the name beside them is already the new one. **What makes it re-read** — the native client re-read and re-tokenized the open diff whenever *anything* in the working tree changed, which cost up to ~140 ms of background work for an answer that could not have moved. It keys per file now, the shape the Tauri client already had: the file's own `stat_stamp`, its `xy`, and the status's `head_sha`. That last one closed a hole in both clients — the working-tree diff is `HEAD` against disk, so a `--mixed` reset changes it while leaving the bytes and the status letters untouched, and neither client had been looking. Phase two also picked up the Tauri client's 80 ms debounce, so arrowing down a file list tokenizes only the file you stop on. - [x] **Cross-client parity, workstream O — the diff learns to be read side by side, on both clients.** The split layout was the native client's one missing diff setting, and on the Tauri client it was a **checkbox in Settings** — a window you leave the diff to open, to change how the diff you were reading is arranged. It is a two-segment control in the diff's own **header** now, in both clients, which is where GitHub Desktop puts it and where the reader who wants the other arrangement actually is; it still persists into the shared `side_by_side_diff`, so the choice outlives the file, the repository, the app and the client. The native layout is **an arrangement of one row model, not a second renderer**: `DiffStore` holds the flat line list either way, and a pair carries *indices* into it, so both columns read the same lines, each side looks up its own syntax tokens by its own flat index with no bookkeeping, and one `DiffLineCell` draws a cell for either layout — the glyphs, the row tints, the tab expansion and the intra-line backplate are written once and cannot drift between the two. The pairing itself stays in core (`build_sbs_pairs`), so the two clients cannot arrange one diff differently; it crosses the bridge as a `u32`-indexed record, and **only while the split layout is on screen** — which is now true of the Tauri client too, where the pairs had been built and serialized for every diff read whether or not anything looked at them. Changing the layout is therefore a re-read, and it goes through the seamless path: the publish step compares the line model and the pairing separately, so the rows and their syntax colour survive the switch, the two arrangements are branches *inside* one `ScrollView` rather than two of them, and the pane changes on the frame its data arrives instead of blanking. Finding that path also turned up a defect it depended on: the Tauri client's *hide whitespace* toggle had been calling the diff loader without `force`, so the loader's "this file is already open" short-circuit returned before reading and the open diff never re-fetched — the setting only took effect on the next file you clicked. Both open panes now re-read on either setting, from one derived key rather than a per-setting effect. Config also gained a second writer, so the chained write moved out of the Settings form and into the store: two quick changes land in the order they were made across surfaces, not merely within one form, and neither surface can revert the other's field. - [x] **Cross-client parity, workstream N — the native changes list stops being one row at a time.** The highest-frequency action in the app — include or exclude a file — had no keyboard route in the native client at all, and the list could hold one selected row, so discarding thirty files meant thirty right-clicks, thirty confirmations, thirty `git` runs and thirty full reloads. The list is now `List(selection: Set<String>)`, which brings shift-click and shift-arrow from AppKit rather than from hand-tracked anchors, and `contextMenu(forSelectionType:)` already hands the menu the whole selection when the right-click starts inside one — so **Discard N Selected Changes…** and its single bulk call came almost for free. **Space** toggles inclusion across the selection, by the select-all checkbox's own sentence, deliberately: *any excluded → include them all, otherwise exclude them all*, so a sweep plus two presses leaves exactly that sweep included whatever state its rows were in. The select-all checkbox itself is finally **tri-state** — `Toggle(sources:isOn:)`, the only route to a mixed checkbox in SwiftUI — where the binary one it replaced read *off* over a list that was mostly on, which is a lie told by the one control people use to answer *what is going in?* at a glance. A `Set` cannot say which row a gesture landed on, so which file the diff pane shows became its own rule in one place: a single-row selection is the choice and the pane follows, a multi-row one leaves the pane where it was — extending a selection is choosing a group to act on, and the diff being read while a discard selection is built around it is the one thing that should not move. **Renames render `old → new`**, both sides truncating filename-first, where showing only the destination had made a rename indistinguishable from an add. Nested repositories and dirty submodules **swap the status letter for a ↪**, because the letter is the part that would be wrong — an embedded repo reports as untracked, a dirty submodule as modified, and both readings invite exactly the expectation that gets people, that the folder's files are what goes in. That replaced a text tag that ate the row's width and put the explanation on the badge and on the disabled checkbox, which is the control someone actually clicks when they want to know why the commit won't take their change. Discard moved from a system confirmation to a **sheet**, for two things a confirmation cannot do: stay up saying *Discarding…* while thirty files are rewritten, and hold its own refusal, which FRONTEND §6.13's refinement keeps inside the dialog that raised it. It is presented from the root's one sheet slot rather than adding a second, since a window has exactly one. Row-action failures now split the way the contract has always said they should, through one `ActionFailure` value and one modifier the sync and branch surfaces adopted too: discard and ignore take the window with a retry, reveal and open-with go to the strip — which grew a ✕, because nothing else can retire it, where the poll's own banner is retired by its own recovery. Two standing wastes went with it: a discard or an ignore now re-reads the **status only**, not a 500-commit `git log` and a progress-bar flash, since neither can move `HEAD`; and `PathText` holds its fitted path in state instead of re-deriving it on every body evaluation, which had been charging ~log₂(path) text measurements per visible row on every hover, selection change and checkbox click. The composer gained the 72-character counter (advisory — nothing is ever truncated, since a silent hard cap chops pasted and AI-generated summaries with no warning), the medium-weight filename that marks an included row, a tooltip only on a path that was actually shortened, a keyboard-reachable resize handle that writes `UserDefaults` once per drag rather than once per frame, and a lock while the embedded-repo confirmation is up — the store is not `isCommitting` yet, but Confirm commits the files the dialog was opened with, so anything typed behind it would be dropped or cleared by a commit it never described. - [x] **Cross-client parity, workstream M — the native client learns to be told what to open, and where its shortcuts live.** Being told which repository to open had never reached the native app. A folder is named from outside — `open -a LeoGit <dir>`, a drop on the Dock icon, Finder's *Open With* — and the app opens it; on macOS that whole hand-off is one callback: `Info.plist` declares `public.folder` under `CFBundleDocumentTypes`, so LaunchServices activates the running instance and delivers the folder to `application(_:open:)`, cold start and warm alike. No socket, no second process to forward from, no window to raise by hand — and Finder's *Open With* and a drop on the Dock icon come with it for free. The resolution rule is core's own `resolve_launch_target`, newly exported, so a subdirectory still walks up to its repository root and a bare launch still just focuses the window. (The `leogit` shell command `install.sh` writes still targets the Tauri bundle — the native app has no release artifact, so giving it a branch is a packaging decision left open in the plan.) A folder that **isn't** a repository yet is the case the whole thing exists for: it raises *Create a repository here?* over whatever is on screen — the picker, another repository, a first launch — naming the folder and saying that creating one leaves the files where they are. Core's pending-target slot deliberately stayed unexported: it can hold the argv target but not the later ones, and a process global the UI has to poll is not a slot the UI can observe, so one observable store owns both routes. Two things about that store are load-bearing. The launch path **claims the target itself** rather than trusting a view modifier, because `.onChange` cannot see a value that was set before it existed — which on a cold start is exactly what happens, the delegate having fired before any SwiftUI task ran; and it reads a *kept* copy rather than the claimable one, because the two consumers run in the same turn and their order is not fixed. **The menu bar is now where the app's chords are written down**, which on macOS is where they belong: File ▸ Clone Repository… (⇧⌘O), View ▸ Changes / History (⌘1/⌘2), View ▸ Show/Hide Terminal, View ▸ Refresh, a Branch menu, and the existing Repository ▸ *proposal* (⌘P). Moving ⌃` off the panel's own toggle and onto its menu item is not cosmetic: a key equivalent on a *button* is matched through the responder chain, which SwiftTerm sits at the head of, while a **menu** equivalent is matched before the chain is consulted — the chord now works from inside the terminal, which is the one place it matters most. The Branch menu is the toolbar control's items rendered a second time from one shared definition, so the two cannot drift into offering different actions; its closures post, so a menu-bar Merge opens the same sheet a click does. There is no ⌘B: AppKit matches key equivalents by walking *into* submenus, so no chord opens a menu, and binding it to one of the items would give the same chord different meanings in the two clients — recorded as a divergence rather than faked. Because a menu-bar menu also has no "about to open" hook, the branch list re-reads on app activation too, which is when a branch created in a terminal has most likely just appeared. Finally, the **release check** ships natively: once per launch, retried every thirty minutes *only while attempts keep failing* — any answer ends it, "you are current" included — gated on the OS connectivity signal alone and never on the git circuit-breaker, whose openness says nothing about the GitHub API in either direction. One `UpdateChip` renders in the toolbar and on the picker, offering the install one-liner to copy, the release page, and a dismissal that lasts the session and is deliberately not persisted. `NetworkPathObserver` grew keyed recovery subscribers so the check's retry sits beside the repository catch-up instead of needing a second `NWPathMonitor`. - [x] **Cross-client parity, workstream J — what the Tauri client does when you are not looking at it.** Every background loop was a flat `setInterval` with no idea whether the window was on screen: a 2 s status poll and a 30 s fetch ran at the same rate minimized as frontmost, or at whatever rate the WebView's throttling happened to allow, which is not a policy so much as the absence of one. The cadence is now the **window's activity ladder**, ported table-for-table from the native client and shared by both: 2 s frontmost, 10 s visible but unfocused, 30 s hidden, with the automatic fetch stretched ×3 while hidden. Neither loop ever *stops* — a visible-but-unfocused window quietly going stale is the failure the ladder exists to prevent, and a hidden one that keeps ticking slowly is what makes coming back to it show a current screen instead of a catch-up. Only the multi-repo badge sweeps pause, because a badge for a repository in a window nobody is looking at is the one genuinely deferrable thing the app does. `setInterval` cannot express a cadence that changes, so the loops became a **self-scheduling chain that re-decides after every run** — which also means a run can never overlap itself, a state change applies immediately instead of after the current period drains, and "auto-fetch is off" is expressible as a loop that simply parks. **The tier scheduler collapsed from three timers into one with three deadlines**: independent timers come due together on their common multiple, so every ten minutes all three walked their lists at once — three fetch fan-outs in one turn, which is exactly what the sequential fan-out each tier promises is meant to avoid. **An idle repository now publishes nothing.** The poll rebuilt the whole repository state, plus two new `Set`s, every two seconds whether or not anything had moved, and every subscriber in the window re-rendered on it forever; the comparison is of the whole status reply rather than a hand-picked list of fields a later field would silently fall out of, and `stat_stamp` inside it is the only reason an idle repository is recognizable at all — porcelain v2 carries no worktree hash, so a file that was modified and still is reads identically without it. That same stamp closed the **stale open diff**: editing the open file in another window now updates the pane within a tick instead of waiting for the row to be reselected, keyed per file, so an unrelated edit elsewhere in the tree re-tokenizes nothing. The poll also stopped spawning `git rev-parse HEAD` every tick — `RepoStatus.head_sha` was already in the reply it had just parsed, which the contract had mandated for months and only the code had not caught up to — and the branch list reloads with the history when HEAD moves, so a checkout made in the terminal moves the menu's checkmark too. The **typing guard stopped being a latch**: it was set from `focusin` and only ever cleared by another `focusin`, so closing a focused terminal panel stranded it at `true` and auto-fetch was silently dead for the rest of the session; the question is asked at the tick now, from `document.activeElement`, which is what the native client has always done. The switcher's identifier fetch was the last unbounded fan-out in either client — one `git remote get-url` per repository, all at once, fifty processes in a turn on a machine with fifty repos — and now runs four at a time. Also on both clients: a once-per-session 0–30 s skew on the first automatic fetch, so two windows over the same repositories don't contend for `index.lock` on the same beat forever, and the native badge cache stopped rewriting itself with an identical value every tick. - [x] **One exclusion rule, in core, with a grace window.** Shipped with workstream J. Unchecking a file in the composer is an opt-out, and the two clients disagreed about how long one survives its path leaving the file list — the Tauri client dropped it the same tick, the native client kept it forever, and the native comment claimed they matched. Dropping it is the dangerous half: a formatter rewriting a file in place can make it vanish for a tick, and the opt-out going with it puts the file back in the commit with nothing on screen saying so. The failure modes are not symmetric — an over-long opt-out costs one checkbox click, a premature one costs a commit nobody meant to make — so the rule is native's, plus a grace window, and it lives in `core::exclusions` where it can only be written once. The window has two terms because the cadence ladder in the same change breaks either one used alone: it is wall-clock rather than a count of ticks, since a tick now means anything between two seconds and thirty — and it *also* requires two consecutive misses, since at the slow rung one read is charged the whole thirty seconds and a time-only rule would prune on the first look, which is exactly the look that can land mid-rewrite. Both counters advance on every tick rather than on a changed file list, since a path is dropped for having been *absent* long enough — which an unchanged list keeps being true of — and a single reappearance resets both.
- [x] **Cross-client parity, workstream I — the Tauri terminal's transport, and the gap at the start of every session.** The panel used to ask for a shell and *then* subscribe to it. Registering the output and exit listeners took two async IPC round trips after `start_terminal` had already returned, the reader thread was emitting the whole time, and a Tauri event with nothing listening is dropped rather than queued — so a fast shell's opening prompt could vanish, and a shell that died instantly on a broken `.zshrc` could lose its error output *and* its exit notice, leaving the panel to close on nothing. Narrowing that window was never the fix. The session's stream is now a **`Channel` the frontend builds with its handler already attached and passes into `start_terminal`**, exactly as the UniFFI bridge has always passed a listener into the spawn: the id is minted in the JS constructor before any IPC, so the handler exists before Rust can possibly hold the channel and the race stops being representable. Two message shapes ride it, `{event:"output"}` and `{event:"closed"}`, pinned by the host crate's first two tests — the TypeScript that reads them is hand-written, and nothing between the two languages would notice a serde rename. The close message can now **overtake `start_terminal`'s own return**, which is what a shell dying that fast means, so the panel records that the session ended and refuses to adopt a pid the backend has already dropped. With it, `start` / `resize` / `close` moved off the main thread (`close_terminal` alone blocks ~250 ms in portable-pty's kill escalation) while **`write` deliberately stayed synchronous**: Tauri runs a sync command inline in IPC arrival order, and that order *is* the keystroke-ordering guarantee. **⌃` is now the toggle, not ⌃-or-⌘`** — ⌘` is macOS's window cycling, and answering to it took a system gesture away from every user of a macOS build; the narrowing had to land in xterm's key handler and the window handler together, since they are one rule written twice and the chord is unreachable from inside the panel if they disagree. **It also stopped being gated on focus.** `MainLayout`'s "a field has focus, leave it alone" bail had been swallowing it in the commit composer since the chord existed — a fault the native client never had, since a SwiftUI `keyboardShortcut` is a key equivalent and fires ahead of the first responder. Opening the terminal from a half-written message is a normal thing to do; it is where you go to run what you are about to describe, and nobody types `Ctrl` + `` ` `` into prose. The general shape of that bug is worth keeping: the bail is the exception, and putting a chord below it asserts that someone might be typing it. **A URL now needs the modifier** — ⌘-click on macOS, Ctrl-click elsewhere, matching SwiftTerm and every other emulator — because a plain click belongs to selecting text, and dragging across a line that happened to contain a URL used to navigate away from it. What that costs in discoverability is paid back by hovering, which names the gesture the way Terminal.app does, and it had to be: xterm's link addon exposes no way to make its own underline conditional, so a gated link that said nothing would just look broken. **OSC 52 works**, so `vim` and `tmux` can set the system clipboard — including from the far side of an SSH session, where nothing else can reach it. xterm ships no clipboard support at all, so the handler is ours, and it is **write-only on purpose**: the sequence's read form types the clipboard back down the TTY, which is an exfiltration route for anything that can print to a terminal, so it is swallowed rather than answered. The write goes through `tauri-plugin-clipboard-manager` rather than `navigator.clipboard`, which WebKit refuses without a recent click — and a shell asking for the clipboard has none. Also: coming back to the app puts the caret back in the shell, since WebKit leaves the emulator painted as focused over a textarea holding nothing and every keystroke vanished until you clicked; the header strip reads **Terminal** before a session names itself, as the native strip already did; and 280 now means the *emulator* in both clients rather than the whole dock in one of them, which had been quietly costing the Tauri shell two rows. ## What's next


- [x] **Claude CLI failures surface their real error.** A non-zero exit with an empty stderr (the CLI puts API/auth errors in the stdout JSON envelope) used to show a bare "Claude CLI failed:". `claude_failure_message` now falls back stdout-envelope → stderr → stdout → exit status, so the message is never blank. Covered by unit tests plus an `#[ignore]`d fake-CLI e2e test in `commands::ai::tests`.
- [x] **Windows: make the embedded terminal actually usable.** The terminal launched Windows PowerShell with a broken `PATH` and most commands failed. Root cause: `start_terminal` copied `std::env::vars()` over the environment `CommandBuilder` had already assembled — discarding the `HKLM`+`HKCU` registry merge portable-pty performs and replacing it with the parent's. Launched from Git Bash that parent `PATH` is MSYS-style (`/usr/bin`, `/c/Program Files/...`), which Win32 cannot resolve at all. Removing the copy restores the same `PATH` Explorer and Windows Terminal give their children; `session_env` now returns only deliberate additions and is covered by `session_env_never_overrides_path`. Alongside it: **shell choice** — new [core/src/shell.rs](core/src/shell.rs) probes for Git Bash (registry install root, launched `--login -i` with `CHERE_INVOKING=1`), pwsh, Windows PowerShell and cmd, exposes them via `list_shells`, and persists the pick as `config.terminal_shell` (Settings → Terminal); an uninstalled preference falls back instead of failing. **UTF-8 corruption** — output was decoded per 4 KiB chunk with `from_utf8_lossy`, so any multi-byte character straddling a read boundary became a permanent U+FFFD; a stateful `Utf8Decoder` now holds the truncated tail. **Rendering** — xterm is told `windowsPty {backend, buildNumber}` (via the new `terminal_pty_info`) so reflow is enabled, and the `ResizeObserver` is debounced 80 ms so dragging the panel no longer triggers a PSReadLine repaint per frame. Terminal IPC moved behind `terminalApi` in `api/commands.ts`; `lazy_static` was replaced with `std::sync::LazyLock` and dropped as a dependency.

- [x] **Windows: `git init` produced `master`, not `main`.** `init_repo` probed `git config --get init.defaultBranch` across *all* scopes to decide whether the user had a preference. Git for Windows ships `init.defaultBranch = master` in its **system** config (`C:/Program Files/Git/etc/gitconfig`), so a vendor default was read as a deliberate choice and every repo LeoGit created on Windows landed on `master`. The probe now runs with `GIT_CONFIG_NOSYSTEM=1`, restricting it to the global and local scopes a user actually sets. This is what `init_repo_names_the_default_branch` had been failing on.

- [x] **Settings unreachable when discovery finds no repositories.** The picker showed a bare "No repositories found" with no way out: the app's only Settings entry point lived in `MainLayout`, which never mounts without a repo, so a user whose `scan_paths` matched nothing could not reach the setting that would fix it.
