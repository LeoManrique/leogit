# leogit — Roadmap

What's shipped lives in [DESIGN.md](DESIGN.md). This file tracks **what's next**. Items are added as they're discovered; check a box only when it ships.

## Recently completed

- [x] **Native sync — fetch / pull / push (fourth Phase-2 flow of the SwiftUI plan), proving the `EventSink` callback seam.** The toolbar gains the Tauri header's sync semantics in native shapes: **Pull** renders only when the branch has real upstream tracking (behind count in the title), **Push** is a split button (`Menu` + `primaryAction`) that re-labels to *Publish Branch* when a remote exists but the branch is untracked — same handler, `set_upstream` derived as `!has_upstream` at click time, never synthesised (core's inferred-upstream fallback deliberately leaves that flag false precisely so a first push carries `--set-upstream`) — and **Force Push (with Lease)** appears in the menu only while the branch has diverged (`has_upstream && ahead > 0 && behind > 0`), behind a destructive confirmation; with-lease is the only force mode core offers. A **Fetch** menu item and a silent warm-up fetch on repo open stand in for the Tauri client's auto-fetch (no background polling natively yet); a remote-less repo disables Push with an explanation, since gh-publish isn't ported. One operation runs at a time (the Tauri `activeNetworkOp` slot), Refresh is held back during transfers the way the Svelte poll pauses, and errors show git's text verbatim. **This is the first flow where core calls back into Swift**: `fetch`/`pull`/`push` are the bridge's first async exports (`async_runtime = "tokio"` — core's `spawn_blocking` needs a live runtime context; the `uniffi` dependency gains its `tokio` feature) and progress crosses its first foreign callback interface — `SyncProgressListener` (`#[uniffi::export(foreign)]`), fed by a `ProgressSink` adapter on core's `EventSink` seam that translates `GitProgress` (its `op` is a `&'static str`, which can't cross the FFI) into a flat `SyncProgress` record: core-computed aggregate percent plus git's raw progress line, rendered as a progress strip under the toolbar. Ticks arrive on core's stderr-reader thread and hop to the main actor, dropping stragglers by generation; completion is the `await` returning, since core emits no terminal event. Verified: zero-warning `xcodebuild`, 117 core + 9 bridge tests — two new end-to-end suites against throwaway repos pin publish→fetch→pull (progress ticks observed crossing the seam, `--set-upstream` flipping `has_upstream`, fetch leaving the working tree alone) and the full force-with-lease ladder (plain push rejected on divergence, lease rejected while the remote-tracking ref is stale, accepted after fetch) — clippy-pedantic clean in bridge and host.

- [x] **Native branch management + merge (third Phase-2 flow of the SwiftUI plan), and the first flow where the native client leads.** A toolbar branch menu shows local branches as an inline `Picker` (checkmark = current, matching by name against `status.branch` like the Tauri client, so detached HEAD marks nothing), remote branches as buttons (picking one runs core's tracking-branch DWIM), plus **New Branch…** (sheet; create off HEAD then switch — the Tauri two-call sequence), **Delete Branch** (local, non-current only; a destructive `confirmationDialog` warns that unmerged commits are lost, since core's delete is always `git branch -D`), and **Merge into "current"…** — a submenu picks the source, then a sheet previews how many commits it brings in (`count_commits_to_merge`, which the Tauri frontend never used) and offers Merge / Squash & Merge. That merge flow existed in the Tauri client only as unreachable dead code (`MergeOverlay` is wired but nothing sets `showMerge`), so the native client ships it first. Failed merges come back as data (`MergeResult`), never exceptions: conflicts show git's own text in an alert, the conflicted files appear in the changes list (`!` badge), the subtitle gains a *merging* marker (`is_merging` folded into every refresh, like the Tauri poll), and the branch menu grows **Abort Merge…** until the merge concludes. Along the way a real core bug got fixed rather than ported: `list_branches` showed a phantom `origin` row because `refs/remotes/origin/HEAD` short-forms to the bare remote name under a custom `--format` (the old `" -> "` filter could never fire there); the skip now keys on the full refname, keeps legal `foo/HEAD` branch names, and is pinned by a clone-based regression test. Exported 1:1 over UniFFI (10 functions, 2 flat mirrors — no `EventSink`, no new representability issues); `rename_branch`/`delete_remote_branch` stay unexported since no client has UI for them. Verified: zero-warning `xcodebuild`, 117 core + 7 bridge tests (branch lifecycle and fast-forward/squash/conflict/abort end-to-end against throwaway repos), clippy-pedantic clean in bridge and host.

- [x] **Native commit flow (second Phase-2 flow of the SwiftUI plan).** The native client now commits: every file row has an include checkbox (checked by default, with a toggle-all header and an "N of M files included" count), and a composer under the list takes a required summary plus an optional growing description (`TextField(axis: .vertical)`), with a prominent ⌘↩ **Commit N Files** button that stays disabled without a summary or checked files. The port mirrors what the Tauri client *actually* does — there is no staging-area concept: two calls, `format_commit_message` then `commit(repo, message, files, amend)`, where core resets the index and re-stages exactly the checked files (whole-file `git add`; `update-index` for deleted/renamed entries). Research confirmed per-hunk/per-line staging (`diff::generate_patch` + `DiffSelection`) is dead surface even in the Tauri frontend, so it remains a follow-up for both clients — and the `DiffSelection` `usize` UniFFI blocker is deferred with it. Inclusion state is an exclusion set (`CommitStore.excludedPaths`, the Tauri client's `userDeselected` semantics), so files that appear after a refresh default to checked; dirty submodules are never committable, and committing an embedded repo asks for confirmation first (it records a gitlink, not files). Failures surface inline with the draft preserved; success clears the composer and reloads status + history. Verified: zero-warning `xcodebuild`, 116 core + 5 bridge tests (a new one pins commit-only-the-selected-files end-to-end against a throwaway repo), clippy-pedantic clean in bridge and host.

- [x] **Native diff view (first Phase-2 flow of the SwiftUI plan).** Selecting a changed file in the native client now renders its diff: file list + detail in an `HSplitView`, line-number gutters, add/remove row tints, intra-line change backplates, and GitHub-palette syntax colour (`Design/DiffPalette.swift`, the same values the Tauri CSS assigns, so the future re-skin colours identical tokens identically). The bridge exposes the same three-step pipeline the Tauri client uses — `get_diff` → `parse_diff` → `tokenize_diff` — keeping its two-phase render: structure paints immediately as plain text, blob-backed tokens recolour in place. Two small core changes made this possible: `highlight::tokenize_diff` is now `pub` (native clients consume tokens directly instead of the HTML `highlight_diff` renders for the WebView), and `IntraLineRange` uses `u32` code-point indices like `Token` (which also makes the whole diff model `#[uniffi::remote]`-representable). `parse_diff` crosses as a purpose-built `DiffPayload` record because core's `ParsedDiff` also carries phase-1 HTML and side-by-side pairs — WebView presentation Swift shouldn't marshal. Token ranges are code points, so Swift styles through `AttributedString.unicodeScalars`, never `characters`. Verified: zero-warning `xcodebuild`, 116 core + 4 bridge tests (a new one pins the flat-index parallel-array contract end-to-end against a throwaway repo), clippy-pedantic clean in both changed crates.

- [x] **SwiftUI scaffold + UniFFI bridge, first vertical slice (Phase 1 of the SwiftUI plan).** A native macOS client (`apps/swift-ui-app`) now renders **real `leogit-core` data** — pick a folder → resolve its repo root → working-tree changes + commit history — through `leogit-ffi`, a UniFFI 0.32 crate that is the third workspace member and the macOS twin of the Tauri shim layer. **Core stayed dependency-free**: rather than adding `uniffi` derives to `leogit-core`, the bridge mirrors its types with `#[uniffi::remote(Record)]` / `(Enum)`, which must restate each struct field-for-field — so drift in core becomes a compile error in the bridge instead of a silent wire mismatch. `scripts/build-rust.sh` builds the static lib and regenerates the bindings, and Xcode runs it as a pre-build phase, so the Swift API can never be stale relative to the Rust it calls (`ffi/generated/` is gitignored for the same reason). Four things had to be got exactly right, all now documented in TECHNICAL.md → *Swift host (UniFFI)* and guarded by assertions in the build script: the bindings import the C shim behind `#if canImport(LeoGitCoreFFI)`, so a modulemap named anything else **fails silently** rather than erroring; core's `reqwest` → `hyper-util` chain needs `SystemConfiguration`, declared via `--link-frameworks` so the requirement travels with the library; Xcode 26 defaults new app targets to `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, which **breaks** generated bindings (mozilla/uniffi-rs#2818), so the target is `nonisolated` and UI types opt into `@MainActor` explicitly; and every core call blocks on a `git` subprocess, so each `GitBridge` wrapper is `@concurrent` (SE-0461) to keep the work off the main actor. Swift 6 language mode, macOS 26 deployment, XcodeGen `project.yml` as the source of truth (the `.xcodeproj` is generated and gitignored). Verified: clean `xcodebuild` with zero warnings, workspace green (116 core + 3 bridge tests), and a headless probe exercising the same bindings against this repo. Build with `just mac-run`.

- [x] **Monorepo restructure + Tauri-free `leogit-core` (Phase 0 of the SwiftUI plan).** All Rust logic moved out of `tauri-app/src-tauri` into a framework-free workspace crate `core/` (`leogit-core`), leaving the Tauri host as one `#[tauri::command]` shim per function over it — the prerequisite for a second (SwiftUI/UniFFI) client sharing one codebase. Repo is now a Cargo workspace: `tauri-app` → `apps/tauri-app`, `target/` + `Cargo.lock` at the root, and the whole tree bumped to the **2024 edition** (`std::env::set_var` gained its now-required `unsafe`; edition-2024 `collapsible_if` let-chains adopted). The one framework seam is `events::EventSink` — core's four streaming commands (`git::{pull,push,clone_repo}`, `terminal::start_terminal`) take an `Arc<dyn EventSink>` and hand it `CoreEvent`s, which `TauriEventSink` maps onto the identical `git-progress` / `terminal-output-{pid}` / `terminal-closed-{pid}` window events, so the extraction is invisible to the Svelte frontend (untouched). `render.rs` (structured diff → HTML) stays in core as the web-host renderer; SwiftUI will consume the same structured `FileDiff`/`Token` types directly. Verified warning-neutral against the pre-restructure baseline: workspace builds clean (debug + release `.app`/`.dmg`), all 116 core tests pass, clippy host-clean. The pre-monorepo design is preserved on the `legacy/classic-design` branch (== tag `v0.1.32`). Architecture in [TECHNICAL.md](TECHNICAL.md) *(Repository layout / Core / host split)*.

- [x] **`~` scan paths resolve in installed Windows builds.** Discovery found every repo under `pnpm tauri dev` and *none* from an installed build — the picker showed "No repositories found · Searched these folders: ~/Dev/LeoManrique/". Cause: `expand_tilde` read `$HOME`, which isn't part of the environment Windows hands a program. Explorer and the Start menu don't set it; POSIX-flavoured shells (Git Bash, MSYS) do, and a dev run launched from one inherits it — so `~` resolved or silently didn't *depending on who started the app*, and discovery skipped each unresolvable root without a word. It now asks the OS via `directories::BaseDirs` (already a dependency): `FOLDERID_Profile` on Windows, which no environment can misreport, and `$HOME` on macOS and Linux exactly as before, falling back to the passwd entry — so the fix is Windows-only in effect with no `cfg` of ours. Moved into [core/src/paths.rs](core/src/paths.rs) next to the other path-form rules, and split into a pure function taking the home directory so it's testable without mutating process env. Three adjacent problems fixed with it: expansion now accepts either separator and emits the platform's own (`~\Dev` works, and no result comes out half `\` and half `/` — a form that compares unequal to the same folder found any other way); `effective_scan_paths` reports the folders **expanded**, since a list headed "searched these folders" is meant to be checked against the disk; and discovery logs one `[discover]` line per run plus a second naming what it skipped, so this class of failure stops being indistinguishable from "you own no repos". Covered by 6 tests, including `~user` and `~snapshots` staying literal.

- [x] **Repo paths look like paths again on Windows.** Every path the app showed carried the extended-length prefix — the picker's hover tooltip read `\\?\C:\Users\Leo\Dev\ryubing\Ryubing`, and a terminal opened there greeted the user with `PS Microsoft.PowerShell.Core\FileSystem::\\?\C:\…` instead of a prompt. Cause: `std::fs::canonicalize` on Windows *always* returns a verbatim path, and it was called at four separate sites (`discover_repos` for both the scan root and each hit, `repo_root`, `init_repo`, `resolve_launch_target`). PowerShell can't map a verbatim path onto a `PSDrive`, so it falls back to a provider-qualified location — which also means anything doing string work on `$PWD` sees that, not a path. New [core/src/paths.rs](core/src/paths.rs) owns the conversion and is now the only canonicalizer in the codebase; it wraps [`dunce`](https://lib.rs/crates/dunce), which strips the prefix **only** when the legacy namespace can express the same path (not over `MAX_PATH`, not a reserved DOS name like `CON`, not a network share), so nothing that needs the prefix loses it. macOS and Linux are unaffected by construction rather than by a platform branch: `dunce`'s check is a `const fn` returning `false` there and its `canonicalize` is a re-export of `std::fs::canonicalize`. Two follow-on problems the fix would otherwise have created or left behind: **(1)** `repos-state.json` written by an older build holds verbatim paths that no longer match anything discovery returns, so `last_opened_repo` would silently stop resolving (the app forgetting the open repo and landing in the picker) and `recent_repos` would grow a duplicate per folder — `normalize_repo_paths` converts and de-dupes on every read, idempotent so the file heals itself with no schema version to carry; **(2)** four components had their own `basename` splitting on `/` only, so a backslash path was one segment and a repo with no GitHub remote to name it was labelled with its full path — they now share [lib/utils/path.ts](apps/tauri-app/src/lib/utils/path.ts), which splits on either separator and is deliberately *not* used for git's own paths (git reports forward slashes everywhere, and a separator-agnostic split would cut a filename that legitimately contains a backslash on Unix). Covered by 9 tests, including `repo_paths_are_ordinary_and_agree_across_producers` — the invariant that discovery, `repo_root` and `init_repo` return the identical string for a folder, since they feed one de-dupe set and the repo caches' keys.

- [x] **Frontend logic migrated behind the IPC boundary.** Roughly 10 KB of pure logic whose inputs already came from Rust now lives in Rust, chosen so no call site gains a round trip (details in TECHNICAL.md, next to each owning feature). The consequential ones: `patch_state` / `record_recent_repo` replace the frontend's two-call load+save of repos-state.json — whose non-atomic read-modify-write was a documented lost-update race worked around with a promise tail — with one locked read-modify-write that returns the authoritative state; `parse_diff` now returns a `ParsedDiff` carrying the phase-1 HTML, the side-by-side pairing, and the +/- totals, and `highlight_diff` returns finished HTML instead of raw tokens, so both render phases share one implementation ([core/src/render.rs](core/src/render.rs)) and per-diff span building leaves the WebView main thread; `get_log` pre-parses co-authors (deleting two duplicated TS copies of the trailer parser) and tag decorations; gitignore path escaping moved next to its Rust-documented contract (`ignore_paths`); `discover_repos` owns the empty-scan-paths fallback. Deliberately *not* migrated: anything inside per-keystroke `$derived`s or scroll-frame paths (fuzzy matchers, arrow-key math, relative dates, `PathText` measurement), where an async IPC call would visibly lag. Also dropped the `serde_repr` dependency (the token wire format it existed for is gone). 18 new Rust tests; the migrated logic is testable for the first time (the frontend has no test runner).

- [x] **In-app update check.** leogit knew how to *ship* releases but never told anyone one existed — users had to re-run `install.sh` on a hunch. Ported LeoSync's updater: one unauthenticated `releases/latest` request per launch, a three-part numeric compare against `CARGO_PKG_VERSION`, and a tinted header chip offering the `install.sh` one-liner (macOS/Linux, copied to the clipboard) or the release-page download (Windows) — see TECHNICAL.md → *In-app update check*. Deliberately not Tauri's updater plugin: that needs a signed release feed we don't have, and nothing here downloads or restarts anything. Failures are silent and retried (immediately on an `online` event, so an offline launch doesn't wait out the window); the check gates on the existing connectivity breaker but doesn't feed it, since a rate-limited GitHub API says nothing about git remotes. Needed a new `os::open_url` (a sibling of `open_path`, no opener plugin) with an https allowlist plus metacharacter rejection for Windows' `cmd /c start`. `LEOGIT_FAKE_UPDATE=<ver>` exercises the chip in debug builds without publishing a release. An adversarial review caught two ways the naive port would have actively hurt users, both fixed: it announced any newer *tag* without checking the release actually contains this platform's artifact — but releases are published one platform at a time, so a partial release would have sent Windows users to a page with only a macOS zip, and on macOS/Linux `install.sh` kills the running app *before* it discovers the artifact is missing — and the lenient version parse both invented phantom updates from prerelease tags and hid real ones behind build metadata. Covered by five tests including `only_plain_three_part_versions_parse`, `unparseable_tags_never_announce_an_update`, and the golden-string `artifact_name_matches_what_the_release_scripts_publish`.

- [x] **Dirty dot in the repo switcher.** Repo rows already showed `↓/↑` for pending pulls/pushes; now a small dot before them marks uncommitted changes, with the hard invariant "dot ⟺ that repo's Changes tab would list files". The old ahead/behind status call used `-uno`, which would have missed untracked-only repos — the mechanics of the `-unormal` swap and the record scan live in TECHNICAL.md → *Git status parsing*. The active repo's dot is fed from the 2 s poll's own file list rather than the background command, and the `repoSync` store's change-equality guard learned to compare the new field (it would otherwise silently swallow every dirty transition). An adversarial review of the invariant surfaced two freshness gaps, both fixed: offline/backoff used to skip background syncs entirely (right for fetches, wrong for a locally-computed dot — they now downgrade to fetch-less recomputes), and repos outside the ~19 tiered recents never got an entry at all (the dropdown now runs a fetch-less sweep of its visible rows). Covered by `repo_sync_status_dirty_matches_changes_tab`.

- [x] **Live push/pull/clone progress + no more mid-transfer freezes.** Two symptoms from one big first push (11 939 objects): the window could stop responding while a transfer ran, and nothing showed how far along it was. The freeze was *not* the push itself (already `(async)`): ~35 commands — `get_status`, `get_head_sha`, `is_merging`, every diff/branch/merge/commit command — were plain `#[tauri::command]`, which Tauri runs **inline on the main thread**, so the 2 s poll spawned 4–6 git processes on the UI thread every tick; a push saturates the repo's disk with pack compression, those normally-instant calls turn slow, and the window stalls for the whole transfer. Every subprocess/filesystem command is now `(async)` (only the pure `format_commit_message` stays sync), the poll gained an in-flight guard, and the new [stores/networkOps.ts](apps/tauri-app/src/lib/stores/networkOps.ts) pauses the poll / auto-fetch / refocus resync / tier scheduler while a user transfer runs — which also makes Push/Pull mutually exclusive. Progress: `process::run_timed_streaming` reads git's stderr incrementally (splitting on `\r` — git repaints its meter with bare carriage returns; unit-tested), [core/src/progress.rs](core/src/progress.rs) ports GitHub Desktop's step/weight parser (8 unit tests), and `push` / `pull` (which gained `--progress`) / `clone_repo` emit throttled `git-progress` events. The UI mirrors GitHub Desktop: the button label flips to `Pushing…`/`Pulling…`, a full-height fill wipes across the button tracking the aggregate percentage, git's raw progress line (`Writing objects:  53% (…), 19.06 MiB | 1.38 MiB/s`) renders in the header's status area, and URL-tab clones get a bar + line in the Clone dialog (GitHub-tab clones go through `gh`, which reports nothing).

- [x] **`leogit <dir>` on a non-repo folder offers to create the repository.** Running `leogit .` somewhere not under version control did *nothing* visible — `resolve_repo_arg` collapsed "no argument", "bad path", and "a real folder that isn't a repo" into a single `None`, so the app just launched or focused with no explanation. It now mirrors GitHub Desktop and offers to fix it. `resolve_repo_arg` became `resolve_launch_target`, returning a `LaunchTarget { path, is_repo }` ([core/src/launch.rs](core/src/launch.rs)) that both the cold-start hand-off and the `open-repo` event carry; only a missing path, a non-directory, or a bare `leogit` still resolves to `None`. `is_repo` now comes from the new `git::repo_root`, which shells out to `rev-parse --show-toplevel` so **a subdirectory resolves to its repo root** (`leogit src/` opens the repo instead of being mistaken for a fresh folder and offered a nested init), falling back to the `.git` probe when the toplevel is unreadable so an existing repo is never offered an init. A non-repo target raises a **Create a repository here?** confirm ([InitRepoConfirm.svelte](apps/tauri-app/src/lib/components/InitRepoConfirm.svelte)) owned by `App.svelte` in every phase, since it isn't scoped to the open repo; confirming calls the new `git::init_repo` (creates the folder if needed, `git init` with `init.defaultBranch=main` unless the user configured one) and opens the result — via `MainLayout.openExternalRepo` (now exported and bound with `bind:this`) when one is mounted, else by entering `main` directly. `init_repo` is idempotent and never nests: a folder already inside a repo returns that repo's root, so a double-confirm — or confirming after the user ran `git init` in a terminal — opens rather than fails. Unborn-HEAD support was already in place, so the fresh repo renders immediately. Covered by 10 Rust tests (`repo_root_*`, `init_repo_*`, and a new `launch::tests` module).

- [x] **Markdown (and prose) diffs now highlight.** A `.md` diff rendered as flat text while every programming language highlighted. Cause: syntect *did* tokenise Markdown (`resolve_language("README.md")` → the `Markdown` syntax), but Markdown tags its text with a `markup.*` scope family — `markup.heading`, `markup.bold`, `markup.italic`, `markup.strikethrough`, `markup.raw`, `markup.quote`, `markup.underline.link` / `meta.link` / `meta.image` — and the `SCOPE_TABLE` mapped only *code* scopes (`keyword`, `string`, `entity.name.*`, …), so `scope_to_class` fell through to `Plain` for every token. Added seven markup `TokenClass`es (`Heading | Strong | Emphasis | Strikethrough | Link | Raw | Quote`, indices 15–21, appended so the `#[repr(u8)]` wire format stays stable) with matching `--syn-*` variables + `.syn-*` rules that carry font styling (bold/italic/strike/underline), not just colour. The existing leaf-first descent colours each construct's delimiter (`#`, `**`, `` ` ``, `[`/`]`) with its body for free. **Fenced code blocks highlight as their info-string language** (```` ```go ````, ```` ```yaml ````, …): the Markdown grammar only *embeds* a fixed subset (Rust/Python/JS yes, Go/YAML/HTML no — those came back as one flat `markup.raw` block, which the first cut then painted a uniform blue), so `tokenize_file` now reads each fence's info string from syntect's own scopes and re-tokenizes the body with that language's parser via `find_syntax_by_token`, uniformly for every language. Unlabelled/unknown fences (`mermaid`, `text`) stay plain, and the table maps only `markup.raw.inline` so a code-fence body never takes the inline-code tint. See [TECHNICAL.md](TECHNICAL.md#diff-syntax-highlighting). Covered by `markdown_constructs_get_markup_classes`, `markdown_fenced_code_block_highlights_by_info_string`, and `markdown_unlabelled_fence_body_stays_plain`. **Follow-up:** the grammar also struck through prose opened by a *single* tilde (`~25 min · ~2 h`, `~/leogit`) — one tilde is a strikethrough opener for Sublime but not for GitHub or VS Code, and unclosed it ran to the end of the paragraph; single-tilde runs are now dropped back to plain (`single_tilde_does_not_strike_through`, `double_tilde_run_survives_across_lines`).
- [x] **Diff syntax highlighting is consistent — tokenise the file, not the diff.** Highlighting looked great on some diffs and mediocre on others. Cause: `highlight_diff` fed syntect only the diff's own lines, but syntect is a stateful, line-sequential parser — a fresh `ScopeStack` starts in a `.svelte` file's top-level **markup** context, so a hunk inside `<script lang="ts">` was tokenised as markup (a `listen<string>` generic came back as an HTML *tag*; comments got no class at all). A markup hunk was right *by accident* (measured 0.0% of characters misclassified) while a script hunk was wrong *by construction* (23.7%). `highlight_diff` now takes an optional `BlobSource` (`workingTree` / `commit`), reads each side's full blob (`git::read_blob` / `git::read_working_tree_file`), parses it from line 1, and maps tokens onto rows by line number — `Delete` from the old blob, `Add`/`Context` from the new. Since the sides no longer share a `ParseState`, a deleted line's unterminated string can't bleed into the rest of the diff either. Unreadable blobs / oversized files fall back to the old path. Also fixed `scope_to_class`, which read only the *top* scope: `//` is `[.., comment.line, punctuation.definition.comment]`, so **every line comment rendered two-tone**; it now descends the stack treating punctuation as transparent, while staying leaf-first so `${name}` in a template literal doesn't inherit `String`. See [TECHNICAL.md](TECHNICAL.md#diff-syntax-highlighting). Covered by `blob_source_highlights_typescript_inside_a_svelte_script_block` (asserts the bug on the legacy path *and* the fix on the blob path), `blob_source_keeps_a_deleted_unterminated_string_from_bleeding`, `comment_delimiter_takes_the_comment_class`, `interpolated_expression_does_not_inherit_the_string_class`, and 6 more.
- [x] **Terminal auto-closes when the shell exits.** Typing `exit` or `Ctrl+D` killed the PTY but left the panel until you clicked ✕. The Rust reader thread already emitted `terminal-closed-{pid}` on EOF and `Terminal.svelte` already listened for it — the event just went nowhere. It now fires an `onExit` prop wired to MainLayout's existing `killTerminalSession`, so the shell exiting takes the same teardown path as the close button. Robust to the platform split where macOS returns EOF and Linux returns `EIO` on PTY read after the slave closes.
- [x] **TypeScript 7 migration (native compiler).** The frontend now type-checks on the stable Go-native TypeScript 7.0 — `pnpm run check:native` runs `tsc --noEmit` in ~0.2 s, replacing the `@typescript/native-preview` dev build's `tsgo`. svelte-check and the Svelte language tools still need TypeScript's programmatic JS API, which the native compiler won't expose until 7.1, so `typescript` is npm-aliased to `@typescript/typescript6` (the official side-by-side layout from the TS 7.0 announcement) and `pnpm check` works unchanged; svelte-check bumped to 4.7.2. TS 6/7's stricter side-effect-import resolution (TS2882) required declaring the two CSS imports via [src/vite-env.d.ts](apps/tauri-app/src/vite-env.d.ts) (`vite/client` types). While verifying, the pre-existing 512 kB chunk warning was fixed by splitting `@xterm/*` into its own chunk (rolldown `codeSplitting` group in [vite.config.ts](apps/tauri-app/vite.config.ts)).
- [x] **Checkout commit (detached HEAD).** Right-click any commit in History → **"Checkout commit"** (disabled on the current HEAD) runs `git checkout <sha>`, landing on a detached HEAD — mirroring GitHub Desktop. A confirmation dialog ([CheckoutCommitConfirm.svelte](apps/tauri-app/src/lib/components/CheckoutCommitConfirm.svelte)) first explains the detached-HEAD consequence. New backend command `checkout_commit` ([core/src/git.rs](core/src/git.rs)) surfaces git's "local changes would be overwritten" refusal verbatim instead of losing work. The detached state is now first-class: `get_status` parses `detached` (from `# branch.head (detached)`) and `head_sha` (free, from `# branch.oid`), and the Header ([Header.svelte](apps/tauri-app/src/lib/components/Header.svelte)) shows `On <short-sha>` + a `DETACHED HEAD` marker and suppresses Push/Pull while detached. The user reattaches by picking a branch (`switch_branch`). Covered by `checkout_commit_detaches_then_branch_reattaches`, `checkout_commit_fails_when_local_changes_would_be_overwritten`, and `get_status_reports_branch_and_head_sha`.
- [x] **Unpushed-commit markers on unpublished branches.** The History view's up-arrow ("not yet pushed") never appeared on a branch with no upstream — clone `main`, branch off, commit, and leogit showed no arrows at all, while GitHub Desktop marks the new commit and leaves the shared base unmarked. Cause: `get_status` only built `unpushed_shas` when `ahead > 0` with a resolved upstream, and `ahead` stays 0 on an unpublished branch. Fix in [core/src/git.rs](core/src/git.rs): when there's no resolvable upstream but the repo has remote-tracking refs, fall back to `git rev-list HEAD --not --remotes` (local commits not on **any** remote). The frontend was already wired ([CommitList.svelte](apps/tauri-app/src/lib/components/CommitList.svelte) badge + [MainLayout.svelte](apps/tauri-app/src/lib/views/MainLayout.svelte)); it just had nothing to render. Covered by the `unpushed_shas_marks_local_commits_on_unpublished_branch` Rust test.
- [x] **Check out remote branches as local tracking branches.** Picking a branch from the dropdown's *Remote Branches* section (e.g. `origin/feature`) used to run `git checkout origin/feature --`, which — because the trailing `--` disambiguates the ref as a commit-ish — left the user in **detached HEAD** instead of on a usable branch. `switch_branch` ([core/src/git.rs](core/src/git.rs)) now probes with `git show-ref --verify --quiet`: a name that isn't a local branch (`refs/heads/<name>`) but is a remote one (`refs/remotes/<name>`) routes through `checkout_tracking_branch`, which derives the local name by dropping the remote prefix (`origin/team/x` → `team/x`, matching `git switch`'s DWIM) and runs `git checkout -b <local> --track <remote>`. The local-first guard keeps a slash-containing local branch from being misread as remote, and a name collision falls back to switching to the existing local branch rather than failing. Mirrors GitHub Desktop's `getBranchCheckoutArgs`; no frontend/API change (the command signature is unchanged). Git semantics verified against a throwaway repo (detached-HEAD repro + all three fix paths).
- [x] **Embedded (nested) git repository support.** A folder with its own `.git` — which `git status` reports as a single untracked directory entry and never recurses into — used to fail to commit with the cryptic `staging produced no changes`, because `update-index --add` silently ignores directory paths. Root cause fixed in [core/src/git.rs](core/src/git.rs): additions now stage through `git add` (new `git_add` helper), which commits the nested repo as a **gitlink** (mode 160000) like the git CLI, while removals keep using `update-index --force-remove`. `get_status` flags such entries `embedded: true` (untracked + trailing-slash path under `-uall`); the UI renders a blue ↪ link badge ([FileList.svelte](apps/tauri-app/src/lib/components/FileList.svelte)) and pops a confirm modal ([EmbeddedRepoConfirm.svelte](apps/tauri-app/src/lib/components/EmbeddedRepoConfirm.svelte)) — "Commit nested repository as a link?" — before committing, since a gitlink (not the folder's files) is a surprising outcome. Fires every time (embedded repos are rare and disappear from Changes once committed). Covered by the `commits_embedded_repo_as_gitlink` Rust test. Same bug exists in GitHub Desktop, which just dumps `git status` and dead-ends.

- [x] **Offline / flaky-connection resilience — the app no longer hangs without a network.** Root cause: every network git command (`fetch`/`pull`/`push`/`clone`/`repo_sync_status`/`delete_remote_branch` + the four `gh` commands) ran *synchronously on the Tauri main thread with no timeout*, so when offline a single blocked `git fetch` froze the window while the 30 s auto-fetch, the tiered scheduler, and on-refocus fetches kept piling on more. Fixed in three layers: (1) all network commands are now `#[tauri::command(async)]` so they run on a worker thread, never the UI thread; (2) a new `process::run_timed` kills any subprocess that outlives its budget (background badge fetches 12 s, user transfers 600 s), and `git_net_cmd` bakes in SSH `ConnectTimeout`/`BatchMode` + HTTP low-speed timeouts so git itself aborts a dead connection fast (unit-tested via `run_timed_kills_a_hung_child_promptly`); (3) a frontend connectivity service ([services/connectivity.ts](apps/tauri-app/src/lib/services/connectivity.ts)) gates *automatic* fetches on `navigator.onLine` + a consecutive-failure circuit breaker (exponential backoff 30 s → 5 min), so we stop hammering an unreachable remote and resume instantly on the OS `online` event or the next successful manual action. `repo_sync_status` now returns a `fetched` flag so the breaker distinguishes a real failure from a no-remote repo. No new UI surface — by design the app just degrades gracefully and recovers on its own.

- [x] **`leogit` shell command — open a repo from the terminal.** `install.sh` now also installs a `leogit()` shell function into the user's login shell, detected from `$SHELL` (zsh → `~/.zshrc`; bash → `~/.bashrc` on Linux / `~/.bash_profile` on macOS; fish → an autoloaded `~/.config/fish/functions/leogit.fish`; unknown shells get a printed snippet). It's written inside an idempotent `# >>> leogit >>>` marker block so re-installs replace rather than stack. `leogit [dir]` resolves the directory and opens that repo in LeoGit — macOS via `open -n --args` (a fresh process whose argv the single-instance plugin forwards), Linux via the PATH wrapper, backgrounded. Paths are canonicalized so they de-dupe against discovered repos; a bare `leogit` just launches/focuses the window. (A folder that isn't a repo yet now raises the init prompt — see below.)

- [x] **Per-repo pull/push badges + tiered background sync.** Each repo picker row shows `↓ N` (behind) / `↑ N` (ahead) badges reusing the header Pull/Push glyphs, so you can see which repos need attention without opening them. ## What's next

- [x] **Claude CLI failures surface their real error.** A non-zero exit with an empty stderr (the CLI puts API/auth errors in the stdout JSON envelope) used to show a bare "Claude CLI failed:". `claude_failure_message` now falls back stdout-envelope → stderr → stdout → exit status, so the message is never blank. Covered by unit tests plus an `#[ignore]`d fake-CLI e2e test in `commands::ai::tests`.
- [x] **Windows: make the embedded terminal actually usable.** The terminal launched Windows PowerShell with a broken `PATH` and most commands failed. Root cause: `start_terminal` copied `std::env::vars()` over the environment `CommandBuilder` had already assembled — discarding the `HKLM`+`HKCU` registry merge portable-pty performs and replacing it with the parent's. Launched from Git Bash that parent `PATH` is MSYS-style (`/usr/bin`, `/c/Program Files/...`), which Win32 cannot resolve at all. Removing the copy restores the same `PATH` Explorer and Windows Terminal give their children; `session_env` now returns only deliberate additions and is covered by `session_env_never_overrides_path`. Alongside it: **shell choice** — new [core/src/shell.rs](core/src/shell.rs) probes for Git Bash (registry install root, launched `--login -i` with `CHERE_INVOKING=1`), pwsh, Windows PowerShell and cmd, exposes them via `list_shells`, and persists the pick as `config.terminal_shell` (Settings → Terminal); an uninstalled preference falls back instead of failing. **UTF-8 corruption** — output was decoded per 4 KiB chunk with `from_utf8_lossy`, so any multi-byte character straddling a read boundary became a permanent U+FFFD; a stateful `Utf8Decoder` now holds the truncated tail. **Rendering** — xterm is told `windowsPty {backend, buildNumber}` (via the new `terminal_pty_info`) so reflow is enabled, and the `ResizeObserver` is debounced 80 ms so dragging the panel no longer triggers a PSReadLine repaint per frame. Terminal IPC moved behind `terminalApi` in `api/commands.ts`; `lazy_static` was replaced with `std::sync::LazyLock` and dropped as a dependency.

- [x] **Windows: `git init` produced `master`, not `main`.** `init_repo` probed `git config --get init.defaultBranch` across *all* scopes to decide whether the user had a preference. Git for Windows ships `init.defaultBranch = master` in its **system** config (`C:/Program Files/Git/etc/gitconfig`), so a vendor default was read as a deliberate choice and every repo LeoGit created on Windows landed on `master`. The probe now runs with `GIT_CONFIG_NOSYSTEM=1`, restricting it to the global and local scopes a user actually sets. This is what `init_repo_names_the_default_branch` had been failing on.

- [x] **Settings unreachable when discovery finds no repositories.** The picker showed a bare "No repositories found" with no way out: the app's only Settings entry point lived in `MainLayout`, which never mounts without a repo, so a user whose `scan_paths` matched nothing could not reach the setting that would fix it. Closing Settings from the picker re-runs discovery so a corrected path applies without a restart. `RepoPicker`'s overlay moved from `position: fixed` to filling its container, since a viewport-fixed overlay covered the very buttons that rescue an empty picker.
